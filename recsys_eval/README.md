# recsys_eval — оценка рекомендаций «Для вас»

Офлайн-оценка рекомендаций на синтетических данных и проверка лент на персонах. В приложении это
не работает и прод не меняет. Выводы — в [`docs/recsys/roadmap.md`](../docs/recsys/roadmap.md),
план онлайн-экспериментов — в [`docs/recsys/experiments.md`](../docs/recsys/experiments.md).

## Запуск

Нужна локальная база с демо-данными: `pnpm db:up && pnpm db:seed`.

```bash
pnpm rec:eval
```

Около минуты. Пишет `recsys_eval/reports/latest.md` и `latest.html` (папка в .gitignore) и
выводит сводку в консоль. Флаги: `--source=db|sim|both`, `--k=10`, `--db-test-days=14`,
`--sim-test-days=21`, `--clients=4000`, `--save-export` (анонимная выгрузка в `data/`).

```bash
pnpm rec:judge
```

LLM-судья (`claude-opus-5-5`) оценивает ленты персон. Ключ берётся из `ANTHROPIC_API_KEY` —
переменной окружения или корневого `.env`, который не коммитится. Без ключа или с `--dry-run`
запросы только записываются в `reports/judge-prompts.md`. Это 18 запросов на прогон.

```bash
pnpm --filter @awaisa/recsys-eval test
```

Тесты метрик, деления по времени и того, что лента прототипов без изменений совпадает с
`rankCandidates`.

## Как устроено

| Файл | Что делает |
|---|---|
| `src/data/exportDb.ts` | Читает базу в `BEGIN READ ONLY`. Телефоны → sha256 с солью, которая живёт только в процессе. Имена, комментарии и авторы не выбираются |
| `src/data/simulate.ts` | Поведение поверх реального каталога: вкусы, свой ритм, привычное место, бюджет, «после А берут Б», 30% ответили анкету |
| `src/data/split.ts` | Деление по времени. Популярность, рейтинги, связи типов и история — только до среза; проверка — что клиент записал после |
| `src/recommenders/production.ts` | Прод-формула: `rankCandidates` импортируется из API как есть |
| `src/recommenders/baselines.ts` | random, popular, popular-in-category и проверочная repeat-places |
| `src/recommenders/shelf.ts` | Правила полки (≤ 2 на место, одно название, слот «Новое место») для прототипов. Тест сверяет их с продом |
| `src/recommenders/prototypes.ts` | Прототипы из roadmap: меняют прод-очки до правил полки |
| `src/metrics.ts`, `src/evaluate.ts` | P/R/NDCG/MAP/HitRate@K, покрытие, разнообразие, новизна, «уже покупал», Hit по новому, 95% бутстреп-интервалы, срезы (cold-start, 1–2 и 3+ визита, ответил анкету) |
| `src/personas/` | Персоны из `docs/ux-testing/personas.md` и судья |

У всех моделей один интерфейс: `recommend(user, context, k) → serviceId[]` (`src/types.ts`).

**Почему TypeScript, а не Python.** Прод-формулу можно импортировать прямо из `apps/api`, без
копии, которая разойдётся с оригиналом. Node 26 запускает `.ts` без сборки. Метрики здесь —
простая арифметика, тяжёлые библиотеки не нужны. Python понадобится, если дойдём до обучения
моделей (пункт 5 roadmap): тогда он будет читать ту же анонимную выгрузку (`--save-export`).

## Чего офлайн не видно

Расстояние, «свободно сегодня», акции и «уже показано» в прошлом неизвестны. Эти части формулы
одинаковы для всех кандидатов и порядок не меняют. Демо-база выбирает услугу визита случайно, а
симуляция — это наши допущения о людях. Цифры показывают направление, а не качество, которое
увидят клиенты.
