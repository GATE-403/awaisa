# AGENTS.md

Turborepo monorepo, pnpm workspaces.

- `apps/web` — Next.js (App Router, `src/`, Cache Components, React Compiler). Read `apps/web/AGENTS.md` before editing it.
- `apps/api` — NestJS (ESM) + TypeORM + PostgreSQL. Read `apps/api/AGENTS.md` before editing it.
- `apps/mobile` — Expo (SDK 58) shell that renders `apps/web` in a WebView. Read `apps/mobile/AGENTS.md` before editing it.
- `packages/tokens` — design tokens (colors light/dark, spacing, radius, typography, durations) as TS. `build` generates `dist/tokens.css` (CSS variables). Used by web (CSS) and mobile (JS).
- `packages/contracts` — the API's request and response types, shared by `apps/api` (type imports only) and `apps/web`.
- `recsys_eval` — offline evaluation of «Для вас» recommendations (`pnpm rec:eval`, `pnpm rec:judge`, `pnpm rec:traffic`); never part of the app.
- `packages/ui` — in-house UI kit for web: Base UI (`@base-ui/react`) primitives styled with CSS Modules on token variables, shadcn-style (source lives here, not on npm).

## UI kit

- Import per component: `import { Button } from '@awaisa/ui/Button'`. Global styles: `@awaisa/ui/styles.css` + `@awaisa/tokens/tokens.css` (imported in `apps/web/src/app/layout.tsx`).
- New component: `packages/ui/src/components/<Name>/{<Name>.tsx, <Name>.module.css, index.ts}`. Wrap the Base UI part, merge `className` with `mergeClassName`, expose variants as `data-*` attributes and style them in CSS.
- Style states via Base UI data attributes (`data-checked`, `data-open`, `data-disabled`, `data-invalid`, `data-starting-style`/`data-ending-style` for animations). Docs: https://base-ui.com/react/overview/quick-start
- Only CSS variables from tokens — no hard-coded colors/sizes. Theme: system by default, force with `<html data-theme='light' | 'dark'>`.
- Base UI is DOM-only, so `packages/ui` does not work in React Native. For native screens, add `packages/ui-native` with the same component API on RN primitives and the same tokens.
- Demo of all components: `/ui` in the web app.
- Components: Menu also has `MenuGroup` (a footnote caption over its rows) and `MenuSubmenu` (a row that opens its own menu beside it). Popover (`@awaisa/ui/Popover`: a controlled inspector anchored to any element — `open`, `onOpenChange`, `anchor`, `label`, `side` — elevated, radius xl, an arrow, no backdrop). ContextMenu (`@awaisa/ui/ContextMenu`: the right-click twin of `Menu` — same popup and `MenuItem`s, compact macOS rows, `display: contents` trigger, `disabled` on touch where a long press means a drag). Menu (`@awaisa/ui/Menu`: `Menu` + `MenuItem` (`variant='danger'`, trailing `icon`) — an iOS pull-down menu by its button; use it instead of a sheet for two or three actions). Input and Select also have `variant='plain'` (borderless, right-aligned value for Settings-style rows; in a `Sheet` row a plain Select opens from anywhere on the row — `Sheet.module.css` stretches the trigger's `::before` over `.row`; never put that rule in the kit: it covered whatever held the trigger, e.g. the catalog's tabs under «Сортировка»). Select's list (the options design to use everywhere): a solid elevated panel ≤ 320px that scrolls inside itself, hairlines between rows inset like Settings (hidden beside the accent-filled highlighted row), fades at the top or bottom while there is more that way (a scroll timeline), a thin trackless scrollbar. Button (primary/secondary/outline/ghost/danger/link/contrast × sm/md/lg), ButtonLink (navigation styled as a button — use it instead of `Button render={<a>}`, which gets `role="button"`), Input, Field, OtpField (one-time code as cells over one real `one-time-code` input — autofill, paste and backspace work; `isInvalid` turns them red with a shake; used on `/login`), Select, Checkbox (incl. indeterminate), Switch, Radio + RadioGroup, RadioCard, Dialog, Skeleton. The set follows the Figma file `Awaisa` (Components section); colors, typography and sizes come from tokens, not from Figma.

## Design system (macOS / iOS principles)

The look follows Apple HIG and the restrained style of apple.com: depth through layers, not borders.

- Layers: page `--color-background` (grouped gray #F2F2F7 / black) → content cards `--color-surface` (white / #1C1C1E) with `--shadow-sm` → floating chrome in matte material `--color-material` + `backdrop-filter: var(--blur-material)` + 0.5px `--color-material-border`. Do not put borders around cards.
- Values come from Apple's macOS 26 UI kit (Figma «macOS 26 (Community)»): system accents (blue #0088ff/#0091ff, red #ff383c/#ff4245, …), label/fill alphas (fills 8–10%, tertiary label 25%), Thick material (#f6f6f6 72%, blur 30) and the 590 «emphasized» semibold. Text-carrying fills (`primary` #0071e3, `link`, `muted-foreground`) stay darker for AA.
- Colors are Apple semantic colors: `foreground` (label), `muted-foreground` (secondaryLabel, slightly darker for AA), `tertiary-foreground`, `subtle` (system fill), `border` (separator, use 0.5px hairlines), system blue/green/red/orange as `primary`/`success`/`danger`/`rating`. Never use palette values in components.
- Type: SF Pro (Text and Display) on Apple devices, Inter elsewhere — no other web fonts (`--font-sans` / `--font-display`). One body size everywhere: `--text-body` 15 for rows, sheets, forms and lists (catalog density), `--text-input` 16 in text fields (iOS does not zoom from 16), `--text-footnote` 13 for secondary text, `--text-xs` 12 captions. Headings step down clearly: `--text-title1` 28 page titles (34 from 768px), `--text-title2` 22 section titles (bold), `--text-title3` 17 group/card/step titles (semibold), uppercase 13 group captions. Titles have negative tracking (`--tracking-tight` / `--tracking-title`). The type tokens are emitted in rem (16px = 1rem, line heights too), so the sizes are the same at the default but follow the browser's own font-size setting; never set a px `font-size` on `html`, and size new text with the tokens, not px.
- Shapes: every one-line control — buttons, fields, selects, search, chips, tab bar, segmented controls — is a capsule (`--radius-control` / `--radius-full`); only containers are rounded rects (cards 16–22, sheets 28, menus 12). Multi-line text areas keep 12. Touch targets ≥ 44px (`--control-height-md`).
- Patterns: Settings-style inset grouped lists (`RadioGroup variant=inset`, uppercase footnote section headers, hairline separators inset 16px, value/chevron on the right), checkmark instead of radio circles in lists, `SegmentedControl`, iOS green switches, floating material tab bar and action bar on phones.
- Reaching a person (client card, booking sheet) is `ContactRows` (`shared/ui/ContactRows`): an inset group of Settings rows with thin glyphs in one quiet colour, no tiles: «Позвонить» (the number on the right), «WhatsApp» (its own round mark, `wa.me`), «SMS»; `surface='page'` on a page background. Never a capsule of bare glyphs.
- Brand marks: WhatsApp, Telegram and Instagram are their real logos in their own colours (`shared/ui/BrandLogo`: `WhatsappMark`, `TelegramMark`, `InstagramMark` — the client and booking sheets, the Telegram rows, profile links, sign-in); brand colours are the one hard-coded colour.
- `LightWave` (`shared/ui/LightWave`) is the app's one burst of light, like two iPhones sharing a contact: a flash at `origin` (a share of its box, `{ x, y }` 0–1, top edge by default), then a wobbling front that runs to the farthest corner and splits into `colors` (2–6 CSS colours or tokens; the system spectrum by default) like light through a prism, a glow trailing it; `duration` (1500 ms), `intensity` (0–1.5), `afterglow` (faint fronts keep coming until unmounted), `onDone`. It fills its box (absolute, inset 0) and plays once on mount — remount with a new `key` to replay. One WebGL fragment shader (`lightWaveRenderer.ts`), light drawn with its own alpha so it reads on dark and light pages; tuned for weak phones: CSS pixels at most (0.75, 0.5 with ≤ 4 GB or ≤ 4 cores or data saver), dropping to a smaller canvas after six slow frames, `low-power`, no antialiasing, a canvas and context of its own per run given back (`WEBGL_lose_context`) when it ends; without WebGL one CSS ring of the same colours, under reduced motion nothing. Used by the sign-in transition and «Вы записаны»; colour tokens become numbers through `shared/lib/cssColor.ts` (`toRgb`).
- Icons: Phosphor (`@phosphor-icons/react/ssr`) for UI glyphs only (`regular`, `fill` for the active tab, `bold` for chevrons). No decorative icons or illustrations — the look is typographic.
- Look follows apple.com/store: page `#f5f5f7`, text `#1d1d1f`/`#6e6e73`, blue `#0071e3` for fills and `--color-link` `#0060c2` for blue text on gray (apple.com's `#0066cc` a hair deeper: it read 4.2–4.5:1 on grey fills); `--color-primary-hover` `#0a66e6` is darker than the fill, so white text stays AA. Two-tone headings: bold title + muted continuation (`PageTitle`). White cards, radius 28, soft `--shadow-sm`, small uppercase eyebrow (`--color-highlight` for "new/hit").
- Controls follow the macOS 26 kit (Figma «macOS 26 (Community)», Buttons / Segmented Controls): flat capsule push buttons, 510 labels. `primary` = Default (accent `#0a6cf0` fill — the kit's #0D6FFF a hair deeper for AA), `secondary` = Bordered Neutral (`--color-fill` 5%), `outline` = Bordered Secondary (accent at 10%, accent label), `ghost` = Borderless, `danger` = Bordered Destructive (neutral fill, `--color-danger-text`). Segmented controls (`shared/ui/SegmentedControl`) follow macOS 26: a capsule `--color-fill` track, equal segments while their words fit (else each as wide as its words, 12pt padding; the knob takes the chosen segment's measured place and width), 46pt tall (42pt segments in a 2pt track), a raised `--color-elevated` knob with a soft shadow that slides (spring) under the chosen segment, the chosen label semibold in `foreground`, hairlines between unselected neighbours. Time/day toggles are neutral fills, pressed = accent. Page headers use `--text-display` (56/60 bold) from 1024px. Toolbars and sidebars (Titlebars and toolbars / Sidebars pages): from 768px the header's icon buttons sit in one 36pt Liquid Glass capsule (Window/Button Group) next to the 36pt accent «Записаться» capsule; on desktop `/map` the list is a floating sidebar (inset 12, radius 20, material, rows highlighted in place with `--color-fill`, radius 8) over a full-bleed map. `/map` has no site footer. Businesses are shown with `BusinessTile` (the owner's logo when there is one — `logoUrl`, uploaded on the cabinet's «Страница» (the camera badge on the logo) through `POST|DELETE /manage/:slug/logo`, 512² WebP, `businesses.logo_url`, on a white plate in the circle; otherwise the white mascot on a vivid circle of the colour picked from the name; frosted white on the vivid no-cover cards).
- Layers in dark: page #000 → card `--color-surface` #1C1C1E → sheet rows `--color-sheet-surface` #2C2C2E on `--color-sheet`; each layer up is lighter, so depth shows without shadows.
- Pictures lead: businesses have a cover (catalog card, business page) and up to 30 work photos tagged with service and master (`Работы` mosaic of the first five, the «Работы» feed); masters have photos (contact-style picker in the master sheet). Without a cover the card shows the tinted `BusinessTile`.
- Restraint: no glow, one primary action per screen, secondary actions as compact `secondary` buttons. No glass/blur effects except the standard material on header, tab bar and booking bar.
- Real-world metaphors: bookings are shown as an e-ticket (`entities/booking/ui/Ticket`: tear-off calendar leaf, perforation with notches, stub with code + barcode; cancelled tickets get an «Отменена» pill, a grey leaf, struck-through time and a faded barcode). Feedback goes through iOS-style toasts (`useToast()` from `@awaisa/ui/Toast`, provider in the root layout): success/error/info; a swipe up, left or right dismisses one (`touch-action: none` on the toast; the covering «Открыть» button takes no pointer — Base UI never starts a swipe on a button — so the tap is read on the toast itself, a press that moved 8px being a swipe, not a tap); `onOpen` makes the whole toast a tap target that opens what it is about, like a notification («Новая запись» → that day in the schedule with the booking open via `?tab=schedule&date=&booking=`; the system notification does the same).
- Weight: cards rest on the page through layered shadows (`--shadow-sm/md/lg`: a tight contact shadow plus a wide ambient one); material panes (header, cabinet bar, business bar, tab bar, sheet bars) carry a lit top edge (`--shadow-material`, `--color-material-highlight`). Under sticky bars content dims through a scroll edge gradient (`--color-scroll-edge`, `::after`) instead of a hairline; on business pages the business bar carries it. Tracking is size-specific: `--tracking-display` for 48–56px headings, `--tracking-tight`/`title` for titles, `--tracking-caption` for 12–13px labels. `prefers-reduced-transparency` and `prefers-contrast: more` swap glass for solid `--color-sheet` panes (and stronger borders/secondary text) in `tokens.css`.
- Mobile performance: no `backdrop-filter` on things repeated per card or over a scrolling feed (favourite heart, hit mark, play mark, tiles, feed chips) — solid or semi-opaque fills instead; blur stays on the few fixed bars. Catalog grids skip off-screen cards with `content-visibility: auto`. Hotlinked CDN pictures are asked for at their shown size with a 2x `srcSet` (`shared/lib/imageSizes.ts` `sizedImage`); catalog cards (`OfferCard`, `BusinessCard`) use `gridImage` — widths 240–840 with the grid's `sizes` (50vw / 33vw / 300px) — which cut the phone catalog's first-screen images from ~1 MB to ~0.6 MB. No virtual list: measured on a production build at 4× CPU slowdown the catalog keeps 60 fps with 72 cards (~2 100 nodes) thanks to `content-visibility`; `next dev` ships ~7 MB of JS against ~1.2 MB, so phone tests over Wi-Fi must use `pnpm build && pnpm start`. Judge speed on a production build (`pnpm build`), not `next dev`.
- Mobile performance (blur): on touch devices that are not iOS (`@supports not (-webkit-touch-callout: none)` + `pointer: coarse`, i.e. Android) `tokens.css` turns `--blur-material` off and makes `--color-material`/`--color-chrome` solid — live blur under sticky bars is recomputed every scrolled frame; view-transition animations are off there too. Never animate layout properties (height, grid rows, top) on scroll; the header's chip row stays put and `--header-height` is written at most once a frame and only on change. Endless animations stop off screen (`OrbitScene` uses an IntersectionObserver). Footer and lower business-page sections use `content-visibility: auto`. `<html data-scroll-behavior='smooth'>` lets Next jump to the top on navigation.
- First-open splash (`shared/ui/Splash`, root layout): plain HTML painted before any script — the mascot hopping over its shadow, the wordmark and «Запись к мастерам — без звонков» on the page colour — once per tab (`awaisa:splash:v1` in sessionStorage, so once per app launch in the WebView), hidden after the page is parsed (≥ 0.9 s, ≤ 2.5 s, fade via `:root[data-splash]`); never for automated browsers (`navigator.webdriver`), and without scripts it leaves after 4 s. Later navigations show the page skeletons.
- Loading skeletons mirror the page they stand for: build them from that page's own CSS classes with `shared/ui/Placeholder` — `TextLine` (a bar inside the real heading or paragraph class, so the line keeps its height, also in flex rows), `Picture` (a picture frame) and `Block` (capsules, circles) — static headings stay as real text («Для вас», «Услуги и цены»). Each page skeleton carries `data-page-skeleton` (at least a screen tall, so the footer never shows and then jumps): `CatalogSkeleton`, `PlaceSkeleton` + `BusinessBarSkeleton` (the `[slug]` layout), `ServicesSkeleton`, `LeaderboardSkeleton`, `ProfileSkeleton`; private pages keep `PageSkeleton`. `/book` shows `BookingSkeleton` (the open card with its question and four service pictures, from `BookingStep` and `ServicePicker` classes; not a sheet — a second sheet would replay the slide-up), and the time step while slots load shows the ruler's own skeleton (big time, ticks, button) instead of capsules. Picture frames (`data-picture-frame`: catalog and «Для вас» cards, places, «Работы мастеров», masters, the place cover) show a quiet fill with the mascot (`--color-placeholder-mark`) until the photo is decoded; the frame's tint is only for places and people without a picture.
- One component per pattern (keep using these, don't hand-roll new ones): uppercase captions over a group are `SectionCaption` (`shared/ui/SectionCaption`: iOS Settings' section header, `as` for the tag, `isInset` (default) puts it 16pt in over an inset group, a count or link may sit inside; never a new `.groupTitle` rule); places with nothing in them use `EmptyState` (`shared/ui/EmptyState`: one look everywhere, like iOS's content-unavailable view: no card or fill, centred where the content would be, the quiet mascot (or an `icon`) over a title3, muted text and `action`; `variant='inline'` is the compact size where results would be; `isOnDark` for the «Образы» stage); emoji in comment fields are `EmojiButton` (`shared/ui/EmojiPicker`: a thin ☺ glyph opening Frimousse in the kit `Popover`, Russian search, loaded on open, data through our own `/emoji-data` rewrite to a pinned `emojibase-data`); people's faces are `PersonAvatar` (`entities/business`: the photo, or the white mascot on the person's own tint — clients, masters, team, reviewers), places are `BusinessTile` (the logo, or the white mascot on a vivid circle of the place's colour), masters as picture cards are `MasterCard` (business page «Мастера» and the booking form's `MasterPicker`, which only adds the radio and the check); nothing draws initials — share images use `OgMascot`; reviews are `ReviewItem` + `Stars` (`entities/review`, the thread look on the business page and in the cabinet, which adds the phone and visit as `meta` and «Ответить / Изменить» as `replyAction`); tabs are `TextTabs` (no rule under them — only the chosen one is underlined; a row wider than the screen scrolls sideways to keep the chosen tab in view; links, or buttons with `onSelect` for local state, `count`, `size='lg'` for a page's main switch — catalog «Места · Услуги», profile «Предстоящие · История», cabinet, map kinds); search fields are `SearchField` (`shared/ui/SearchField`: a borderless fill capsule at the control height with the glass and a clear button — the business page menu, the cabinet's clients); filter chips use `shared/ui/Chip/Chip.module.css` (`chip`, `count`; business menu, services page, «Часто ищут»); long lists use `MoreFade` (inside a group, `ScrollArea`); a section's tools on phones float in `FloatingToolbar` (`shared/ui/FloatingToolbar`: a row in the header with a mouse, one material capsule at the window's foot on phones, `align='center' | 'end'`, hidden when it holds nothing to press; the page pads its foot with `--floating-toolbar-space` — analytics, reviews) (`shared/ui/MoreFade`: the last item fades, «Ещё N …» floats on the fade, «Скрыть» folds it back and stays floating at the bottom of the screen (sticky) while the open list is in view; reviews, upcoming visits, history).
- Speed on phones: the business cover is a width-based `srcSet` (`fluidImage`); edge-fade masks on sideways rows only apply with a mouse (a mask over a scrolling row repaints every frame on phones); popular service cards take their free time from the place's one `next-free` answer instead of a request per card; `optimizePackageImports` covers Phosphor and Base UI. Check speed on `pnpm build && pnpm start`, not `next dev` over Wi-Fi.
- Schedule on weak devices (measured with React `Profiler` on a day of 8 masters and 104 visits, dev build): the pointer's slot lives outside React state (`createHoverStore` in `DayCalendar`, read by one `SlotCursor` per lane through `useSyncExternalStore`) — crossing slots used to re-render the whole day, 204 ms of renders over 12 slots, now 4 ms; a drag sets its target only when the slot or master changes (a fresh object per pointer move re-rendered the day each move); on touch screens cards carry no scroll-driven edge fade (two animations per card meant a compositor layer each). Keep per-pointer-move state out of `DayCalendar`'s own state.
- Visited routes stay in the DOM (Cache Components keeps them hidden with React Activity): never style the shell with `:root:has([data-…])` / `html:has(…)` for something a route renders — it keeps matching on every later page (this once locked scrolling everywhere after `/book`). Set it from an effect instead, which Activity cleans up when it hides the route: `usePageScrollLock()`, `useInertOutside(ref)` (everything around the booking sheet is inert, so Tab stays in it; toasts and the scrim with `data-keep-interactive` stay usable), `useRootFlag('business-bar')` → `:root[data-business-bar]`. Shell-level parts in the root layout (header, tab bar, «Продолжить запись») are fine.
- Gestures and big moving cards (the booking `CardStack`, the «Образы» deck, the time ruler): the finger's path is written straight to CSS variables once a frame (`requestAnimationFrame`, `style.setProperty`, `data-dragging` toggled by hand), never through React state; after the press the rest of the gesture is followed on the window (`pointermove` / `pointerup` / `pointercancel` / `blur`, no pointer capture), so a mouse that wanders far or is let go outside the window still ends it — the card used to freeze mid-drag; on release the drag is cleared at once (not on the next frame), before the cards change places in the same render — otherwise they jumped with transitions still off; the card swiped away keeps the same transform functions as the others so it glides off and fades — re-rendering the form or the deck on every move dropped frames on phones. Moving cards animate only `transform` and `opacity` (`will-change: transform`): no `filter` (drop-shadow over the ticket notches, brightness on back cards) — shadows are a plain `box-shadow` on an unmasked layer, dimming a dark layer's opacity. Big moves settle with `cubic-bezier(0.22, 1, 0.36, 1)` (no overshoot; `--ease-spring` stays for small toggles and indicators). The ruler tells the form its centred time only once it settles (140 ms) and fades its edges only with a mouse.
- Material blur: only `backdrop-filter: var(--blur-material)` in source — Lightning CSS adds `-webkit-`. Writing both by hand makes the minifier drop the standard one.
- Text over pictures: every picture card (offers, places, masters, «Для вас», «Работы мастеров», the booking form's services) uses one scrim, `--card-scrim` (`shell.css`: clear over the top third, eased to nearly black at the foot), and `--card-text-shadow` under its white text (none on white capsules like «Записаться») — light photos used to swallow the words. Never hand-roll a card's own gradient.
- Motion: `--ease-standard`, `--ease-spring` for toggles/indicators; pressed state = `scale: 0.97`. Picture cards (offers, places, «Для вас», «Работы мастеров», masters, the master picker) carry `data-card` and their picture `data-card-media`: one rule in `shell.css` — with a mouse the picture zooms slowly (1.06) inside its frame and the shadow deepens, a press sinks the card (0.97, 80 ms) on touch too; no lift, which sideways shelves would clip; the offer card's «Записаться» turns accent on hover. The catalog card morphs into the business cover with React `<ViewTransition name="business-<slug>">`; phone sheets slide up with a slight settle. Everything is cut by `prefers-reduced-motion`. In the app, `haptic()` (`nativeBridge.ts`) plays taptic feedback (booking done, error, cancel, drag pick-up).
- Destructive buttons in sheets (cancel a booking, delete a photo / promotion / branch / stock item / plan / question) are `HoldButton` (`shared/ui/HoldButton`): a soft red capsule with a glyph (the bin, or ⊗ for cancelling) that fills from the left while held and acts after 1 s; let go early and it drains back, a quick tap says «Удерживайте»; Space / Enter held work too; e2e press them with `click({ delay: 1300 })`. No confirmation dialogs on top of it.
- Reversible actions are not confirmed: cancelling (client or salon) and dragging a booking happen at once with «Вернуть» in the toast (`useToast().show({ action })`); the API keeps a 15 s undo window (`UNDO_WINDOW_SECONDS`, `POST …/restore`) and sends the salon's SMS only after it.
- Dates in sheets are `shared/ui/DateField`: the date in words («31 декабря 2026», «Без срока»), the system picker invisible over it (a tap anywhere opens it, `showPicker`), a small × for optional dates; never the browser's «dd/mm/yyyy» segments (certificates, promotions, masters' leaves).
- Inputs format while typing: `maskPhoneInput` (+996 555 123 456) and `maskAmountInput` (1 500) from `shared/lib/inputMasks.ts`; tel/numeric keyboards and `one-time-code`.
- Copy uses verbs and the next action («Добавьте первую услугу», «Запишитесь к мастеру»).
- Less to read: say only what decides the next tap. Phones get one-line meta, smaller titles (`PageTitle` 22px), no decorative headings where tabs already name the view, optional things behind a link («Добавить комментарий», notification settings, the week's hours, reviews past three). Prefer short facts («Сегодня с 15:30») to sentences («Свободно сегодня с 15:30»).
- Spacing on a 4px grid (`--space-1` = 4px … `--space-20` = 80px). Breakpoints (JS only, literal px in media queries): sm 640, md 768, lg 1024, xl 1280.

## Design taste (the owner's decisions — follow them)

Rules the owner set after rejecting designs. They apply to every new screen.

- The design philosophy, the order rules win in and how patterns are remembered: `docs/design/README.md`. The full do / don't catalogue is `docs/design/patterns.md`: read it before any UI work and check the result against it before showing it (the `design-check` skill in `.claude/skills` does both). When the owner rejects or praises a design, add a row there in the same turn.

- No cheap UI. A «Ближайшее время» card made of a surface card, a tinted glyph in a circle, a title over a subtitle and three wide equal capsules with the day stacked over the time was rejected as «очень дешево, никогда не делай такой дизайн». «Для вас» redone as white row cards (a 64px thumbnail, a reason line, name, price · place) with ‹ › paddles was rejected the same way. Both read like generic templates and list UIs, not the app's picture-led catalog.
  - New blocks start from what the app already has: the kit's `Button` capsules, Settings-style inset rows, footnote captions. Use content-width one-line capsules, not stretched grids. No icon unless it is a UI glyph.
  - Picture shelves keep their 3:4 picture cards. To save space, trim spacing or the card size, never swap them for thumbnail row cards.
  - When a request is about size or space, change the spacing first and ask before redesigning the component.
- Quiet profile style (approved: «да так гораздо лучше запомни этот стиль»), the default for profile-like and content pages:
  - One centred column (~640px) right on the page background. No separate cards per section and no big banners.
  - A soft radial wash of the person's or place's colour behind the head. The face is centred: name in title1, status, then one footnote line of facts with bold numbers.
  - Secondary facts (level, dates) are a single footnote line in the accent colour, not rings or progress widgets. Small secondary capsule actions.
  - Sections under iOS-Settings-style uppercase footnote captions with the count on the right.
  - Collections stay compact: small round faces with first names (≤ 6), capsules with logo and count (≤ 4), reviews as a hairline thread of three with the rest behind `MoreFade`.
  - Gamification is colourful but restrained, like 2GIS: each achievement has its own system colour, earned ones are lit like a coin, unearned ones are grey with «2 из 5» and a thin progress line.
  - A gradient banner with an avatar ring was rejected as «дефолтный шаблон ИИ». A photo-led profile (full-width photo melting into blur, big numbers, two-column desktop) was built and rolled back («убого» on desktop). Do not bring back a photo hero, banners or avatar rings unless asked. Even then, show a mockup or ask first, and never just blow up the phone layout on desktop.

## Web app structure

- Architecture: Feature-Sliced Design. Every slice of views/widgets/features/entities has an `index.ts` public API that exports only what other layers use; import slices through it (`@/entities/booking`), never deep. Entities take features through slots (e.g. `OfferCard action`), not imports. Modules with React hooks carry `'use client'` so barrels stay safe for server components.
- Rendering: pages without data are static (SSG: `/business`, `/login`, `/ui`); every other route is Partial Prerendering — a static shell plus server-streamed data. A place's pages (`/<slug>`, `/<slug>/services`) are rendered once and then served whole from the cache (ISR with Cache Components; ~3 ms and ~1 200 pages/s for one Next process instead of ~8 ms of CPU and ~115 pages/s): `generateStaticParams` in `app/[slug]/layout.tsx` gives the build one never-existing `PRERENDER_SLUG` (no API needed at build), each place is drawn on its first visit and redrawn when its data's `cacheLife` runs out (a minute) or `updateTag` drops it. `/<slug>/book` stays per request (`connection()`): the form opens on what the link's query asks for. A client `useSearchParams` puts what reads it off a cached page's HTML until scripts run, so the header reads the catalog's query through `shared/ui/CatalogQuery` (only on «/»). Keep it so: a param no `generateStaticParams` covers (a catch-all in a parallel slot counts: it is a param of every page it matches) or a server read of `searchParams`, `cookies()`, `headers()` there puts them back to a render per request; the second `curl -sD- <url>` of a production build must say `x-nextjs-cache: HIT`. The catalog, `/map`, `/feed` and `/top` read `searchParams` and still render per request (~110-200 pages/s); rewriting their plain addresses to cached twins in a proxy was tried and dropped: the client router keeps one route tree per path, so prefetches of `/?kind=` asked for the twin's segments and their responses never finished. `'use client'` views are still server-rendered to HTML; what matters is where data is read. Public data is server-rendered from the Cache Components cache (`shared/api/serverApi.ts`: `'use cache'` + `cacheLife('minutes'|'hours')` + `cacheTag('businesses' | 'business:<slug>')`); dynamic parts (search params, slugs) stream into the prerendered shell (Partial Prerendering). After an owner saves in the cabinet, `refreshBusiness(slug)` (server action, `shared/api/revalidate.ts`) calls `updateTag`, so the public page is fresh at once. Personal pages read the session on the server too (`shared/api/sessionApi.ts`, server-only: forwards the request's cookies to the API, `no-store`, always behind `<Suspense>`): `requireCustomer(next)` redirects guests to `/login?next=` before anything renders, `getSessionCustomer()` returns null for guests. `/bookings`, `/manage` (one business → straight to its cabinet), `/manage/<slug>`, `/master` (one place → its day), `/master/<slug>` and `/business/new` pass that customer to `SessionProvider` (`entities/session`, seeds `useSession` so there is no `/api/me` round trip) and the first data as `initial*` props; the client hooks skip their first fetch and refetch after edits. `/review/<id>` is rendered on the server from the SMS signature (`getVisitReviewOnServer`); `/map`'s first list comes from the cache (`listMapPlaces(kind)`), «Рядом со мной» refetches on the client. Live bits stay on the client (next free slots, schedule polling, the places marquee).
- SEO (`shared/lib/seo`): `app/sitemap.ts` (static pages, every kind's landing, the leaderboards with someone on them, every business and its services — paged through `listAllBusinesses`, the list answers 60 at most), catalog kinds as landings (`views/catalog` `catalogMetadata`: `/?kind=barber` has its own title, description and canonical from `KIND_SEO`; a sort points back to its page, searches and «Другое» are `noindex, follow`; the catalog carries `WebSite` + `Organization` JSON-LD (`siteJsonLd`, logo `/apple-icon`) and an `ItemList` of its places), each `/top` board its own title and canonical (`boardMetadata`), `/map` and `/feed` canonical to themselves whatever the query, `app/robots.ts` (personal, booking, payment and API paths closed; `/manage`, `/master`, `/bookings`, `/login` as exact-path rules so slugs like `/masterclass` stay open), JSON-LD on the business page (`businessJsonLd`: schema.org type by kind, address, geo, hours, aggregateRating, offer catalog in KGS), `businessMetadata` (title, description, canonical, OG; noindex when unpublished) and generated share images (`app/opengraph-image.tsx`, `app/[slug]/opengraph-image.tsx` — the cover wins when there is one; `ogTint.ts` mirrors `pickTint` because images cannot read CSS variables). Absolute URLs come from `NEXT_PUBLIC_SITE_URL` (default https://awaisa.kg), set as `metadataBase` in the root layout.
- Data: server pages read `getBusiness(slug)` (business + branches + catalog, `notFound()` on 404), `listBusinesses(kind, q)`, `listOffers(kind, q)` and `listPopularServices(kind)`. Dynamic routes pass the `params` promise into `<Suspense>` so the shell stays prerendered. Business data reaches components as props. URL-aware chrome sits in `<Suspense>` in the root layout. Browser calls go through `shared/api/clientApi.ts` to `/api/*`, which `next.config.ts` rewrites to `API_URL` (same origin: no CORS, works in the mobile WebView).
- API outage on the web: every cached public read in `serverApi.ts` goes through `shared/api/readApi.ts` — an 8 s timeout (`API_TIMEOUT_MS`), and on a network error, timeout, 5xx or 429 the last good answer for that path (kept per process, 300 paths) is served and cached for seconds only (`if (isStale) cacheLife('seconds') else cacheLife('minutes')`: `cacheLife` takes literals, one call per run), so pages heal as soon as the API is back; secondary blocks pass a `fallback` (reviews, questions, promotions). A page never rendered while the API is down shows `app/error.tsx` inside the shell; a failing root layout shows `app/global-error.tsx` (its own document). Add new public reads through `readApi`, never a bare `fetch`.
- Coming from outside (2ГИС, Instagram, QR): the cabinet «Филиалы» lists «Ссылки для записи» — one `/<slug>/book?branch=<id>` per branch with «Копировать», so the client lands with their branch chosen. Guests' name and phone are kept after a booking (`entities/booking/lib/contactStorage.ts`, `awaisa:contact:v1`) and filled in next time.
- Client bookings: guests can book without an account; `localStorage` keeps `{ id, token, snapshot }` per booking (`entities/booking/lib/bookingStorage.ts`) and the token lets them view/cancel. Signed-in clients also get the server list (`GET /me/bookings`: their bookings plus any made on their verified number), merged with device bookings on `/bookings`.
- Session on the client: `useSession()` (`entities/session`) (one shared store, fetches `/api/me` once; `status` is `loading | guest | signedIn`), `useRequireSession()` redirects guests to `/login?next=…`. The session is an httpOnly cookie set by the API through the `/api` rewrite — never read it from JS. Booking contacts skip the phone field when signed in. Phones are shown with `formatPhone()`.
- API shapes live in `packages/contracts` (`@awaisa/contracts`, TypeScript only): the web reads them through `shared/api/types.ts` (a re-export), and every API controller handler the web calls declares its answer with them (`Promise<Booking>`, `Promise<Offer[]>` …), so a field renamed, removed or made nullable in the API fails `pnpm typecheck` instead of a page. Adding or changing an endpoint: put the shape in contracts, type the handler, call it from `clientApi` with the same type; name small answers too (`CreatedId`, `CheckoutLink`) instead of writing `{ url: string }` at the call. The API imports contracts with `import type` only (`common/contracts-imports.spec.ts` fails otherwise — Node cannot load the package's .ts at run time). Answers built from raw SQL are typed where the rows are read (`as Offer[]`), which the compiler cannot check — keep the SELECT's aliases equal to the contract's fields.

- Recommendations (`src/recommendations`), built like the big feeds — candidates from every active service, a transparent score, signals from behaviour, variety and exploration: `GET /recommendations?interests&gender&budget&lat&lng&visits=serviceId~YYYY-MM-DD,…&like&recent&session&limit` (`like`: the service being chosen — same kind +4, other kinds −3, same-person services +2, its gender read from its name when none is stated, past places and kinds ignored) (OptionalAuth: a signed-in client's past visits by phone are added). Two bookings racing for one time can also deadlock (40P01); `isOverlapError` reads that as a taken time too, and `DatabaseLogger` keeps both out of the error log.
- Validation: Zod schemas in `*.schemas.ts` via `@Body({ schema })` / `@Query({ schema })` + global `StandardSchemaValidationPipe`. Rate limit per IP: `RATE_LIMIT_PER_MINUTE` (120) and `BOOKING_RATE_LIMIT_PER_MINUTE` (5) for `POST /bookings`; `GET /catalog` is not limited because the web server fetches it for every visitor from one IP (`trust proxy` is on for private networks).
- Awaisa Studio's catalog was seeded by the `SeedCatalog` migration and moved into the platform by `Businesses`; other businesses edit their data in the cabinet.

Templates and the Meta setup: `docs/whatsapp.md`. Mailings and login codes never go through WhatsApp. Clients link from a booking: `t.me/<bot>?start=v<booking id hex><HMAC>` (`client-telegram.ts`, unit-tested, no code table); the owners' bot handles it (`/start v…` links, `/stop` back to SMS).
- Moderation (`src/moderation`, migration `Moderation`): reports are records: table `reports` (`target_type` photo | review | profile, `target_id` (a uuid, or a person's public id), `reason` spam | offensive | fake | explicit | other, `reporter` = `c:<customer id>` when signed in else `s:<device session>`, one open report per thing and reporter); `POST /reports` (OptionalAuth, 204) and the feed's old `POST /feed/:id/report` (`{ reason?, session? }`). Platform admins (`ADMIN_PHONES`): `GET /moderation/queue` (open reports grouped by thing, most reported first, with a preview), `POST /moderation/decisions` (`keep` settles the reports and, as the latest decision, stops automatic hiding for good; `hide` (a photo gets `is_moderated`, which the owner cannot undo, and the owner's Telegram hears `photoModeratedText`); `delete` (a photo with its file, a review, what a person wrote about themselves); `block` for profiles only: `blocked_at`, sessions dropped, sign-in refused in `AuthService.openSession`, their reviews hidden), `GET /moderation/decisions` (the journal with a snapshot of the preview). An owner showing a photo again or deleting it settles its open reports.
- Telemetry (`src/telemetry`, tables `funnel_events` (+ `flow`, `meta` jsonb), `funnel_sessions` (one row per device: its latest coarse profile), `app_errors`, 90 days): `POST /telemetry/events` (202; device session, ≤ 50 steps with optional `meta` codes matching `^[a-z0-9_]{1,24}$` — a typed value is refused —, an optional `device`); the flow is worked out from the step (`FUNNELS` in `telemetry.schemas.ts`, which fails to compile if a contract step is in no flow). For platform admins: `GET /telemetry/funnel?days&flow&type&os&app&textScale&net` (distinct sessions per step of one flow, for everyone or one kind of device, share kept from the previous step and from the flow's start — `buildFunnel`, unit-tested), `GET /telemetry/signals?days` (form errors by field, toast actions by kind, empty searches, wrong codes, failed payments), `GET /telemetry/segments?days` (devices per type, OS, app, font size and network) and `GET /telemetry/errors?days` (grouped by message). `ServerErrorsFilter` (global) records every 5xx/unexpected API error with its route and stack.

- Processes (`src/runtime`): one build, three ways to run. `PROCESS_ROLE` (process environment, validated in `env.ts`): `all` (default, `pnpm dev`) serves HTTP, runs the cron jobs and migrates on start; `api` (`node dist/main.js`) serves HTTP only and can be scaled; `worker` (`node dist/worker.js`, no HTTP, exactly one) runs every `@Cron`, the start-up affinity backfill and the Telegram long-poll / `setWebhook` (`RuntimeService.runsJobs`). `AppModule.forRole(role)` imports `ScheduleModule` only where jobs run, so an `api` process never fires a cron. Split roles refuse to start without `REDIS_URL`: the worker bumps cache tags the api instances must see, and rate limits count across instances. Migrations then run once per deploy with `pnpm --filter api migrate` (`dist/database/migrate.js`); compose has `migrate` → `api` + `worker`, sharing one image and the `x-api-env` block (add new env vars there).
- Monitoring: every server error (`ServerErrorsFilter`), browser error (`reportError` → `POST /telemetry/errors`), Next server-render error (`src/instrumentation.ts` `onRequestError`, posted to the same endpoint as `SSR <route>: …`) and failed cron job (`AppLogger` sees context `Scheduler` → `runtime/job-failures.ts` → `AlertsService` records `Cron: …`) lands in `app_errors` through `TelemetryService.recordError`, which also sends it to Sentry when `SENTRY_DSN` is set (`runtime/sentry.ts`, `@sentry/node` on the server only — the browser carries no SDK; no tracing or auto-instrumentation; `dataCollection` off; `runtime/error-scrub.ts` replaces phones and long numbers and drops query strings; grouped by source + message with ids folded; works with GlitchTip too). `AlertsService` (jobs process, every 5 min) texts `ALERT_TELEGRAM_CHAT_ID` through the owners' bot (`/chatid` tells a chat its id): any new server error, browser errors only in a burst (≥ 10 in a check), Redis not answering; the same alert repeats at most hourly. `.github/workflows/uptime.yml` checks `vars.UPTIME_URLS` from outside every 5 minutes (three tries) and texts the same chat via `secrets.ALERT_TELEGRAM_BOT_TOKEN` / `ALERT_TELEGRAM_CHAT_ID`; it is skipped until the variable is set. `/health` adds `cache: redis | memory` and is 503 only when the database is down. Settings read before Nest starts (`PROCESS_ROLE`, `SENTRY_*`) come from the root `.env` via `loadRootEnv`.
- Rate limits (`cache/rate-limit.storage.ts`, `RateLimitStorage`, the `ThrottlerModule` storage): one fixed-window counter per key in Redis (`rl:<throttler>:<key>`, a Lua `INCR` + `PEXPIRE`, a `:block` key past the limit), so a limit holds across every api instance and a deploy; no Redis or a Redis error falls back to in-process counters, never a failed request. The cache's Redis connection is opened even with `API_CACHE=off` for this.
- Database (`database.module.ts`): `DATABASE_POOL_SIZE` (10) connections per process, `DATABASE_STATEMENT_TIMEOUT_MS` (30 s; the compose worker gets 300 s) cancels runaway queries, idle transactions end after 60 s, a full pool errors after 5 s, `application_name` is `awaisa-<role>`. Queries over 1 s are logged as warnings by `DatabaseLogger` (SQL only, never parameters). Foreign keys are indexed (`ForeignKeyIndexes` migration) — index a new foreign key in the migration that adds it. `pg_stat_statements` is preloaded by compose's Postgres and enabled by the optional `QueryStats` migration; `pnpm --filter api db:slow` lists the 15 queries with the most total time (`-- --reset` clears the statistics). Measured on demo data (16k bookings), uncached: public endpoints under 10 ms, `/recommendations` ~20 ms.
- Free times in bulk (`AvailabilityService.firstFreeTimes`, behind `findNextFree`, `findNextFreeByService` and «Для вас»): the same answer as `getAvailability` day by day, but loaded in about nine queries however many places or services are asked (services, businesses, masters per service, opening windows, bookings and time off over both days, `MasterScheduleService.offHoursBusyMany`), then `buildSlots` in memory — it was ~8 queries per place per day (519 → 9 for the whole catalog). Keep it that way: never call `getAvailability` in a loop; add a batch loader next to the single one (`getActiveServices`, `getSpecialistsForServices`, `findByIds`, `getOpeningWindows`).
- Logs: `createLogger()` — Nest `ConsoleLogger`, one JSON object per line in production. `requestLog` writes `METHOD /path status ms id=…` per request (no query string: it may carry phones), errors for 5xx, `slow` from 1 s, and returns `x-request-id`. HTTP keep-alive is 65 s so a load balancer never reuses a closed connection.

## Accounts, SMS and admin (apps/api)

- Sign-in by phone: `POST /auth/otp` (`channel: auto | sms`) → 6-digit code, sent to Telegram through the Telegram Gateway when `TELEGRAM_GATEWAY_TOKEN` is set (`checkSendAbility` pays, the send with its `request_id` is free, `ttl` refunds undelivered codes) and by SMS otherwise or when Telegram refuses the number; the response says which `channel` was used and the login page offers "Нет Telegram? Получить SMS". The resend cooldown is per channel. The code itself is ours (HMAC-hashed with `AUTH_SECRET`, 5 min, 5 attempts, one per 60 s and 10 per day per number), `POST /auth/verify` → creates the customer if new and sets the `awaisa_session` cookie (opaque token, sha256 in `sessions`, 30 days), `POST /auth/logout`. Phones are normalized to E.164 by `common/phone.ts` (`0555…`/`555…` → `+996555…`). Texts and login codes go only to `SMS_ALLOWED_COUNTRY_CODES` (default `996`; `SmsService.canSendTo`, `isAllowedDestination`): `POST /auth/otp` refuses other numbers with 400 before anything is sent (Telegram codes cost money too), and booking, reminder and waitlist SMS to them are skipped — bookings still go through. A code attempt is taken atomically (`UPDATE … attempts + 1 WHERE attempts < 5 RETURNING`) before the comparison, so parallel guesses get five tries in all.
- Sign-in through the Telegram bot («Войти через Telegram», `auth/telegram-login.service.ts`, table `telegram_logins`; pure `auth/telegram-login.ts`, unit-tested): the page makes a random 43-char token, registers it with `POST /auth/telegram` (`{ token }`, 204; `GET /auth/telegram` says `isAvailable` and the bot) and opens `t.me/<bot>?start=login_<token>`; the bot ties the chat to the token and asks «Поделиться номером» (a `request_contact` keyboard); only the person's own contact counts (`contact.user_id === from.id`, a forwarded one is refused), numbers outside `SMS_ALLOWED_COUNTRY_CODES` too; a chat that already shared its number is signed in at once (`rememberedPhone`; «Готово — вы вошли с номером …», `/stop` forgets it); it confirms the chat's latest open token (10 minutes) and links that number's client messages to the chat. The page polls `POST /auth/telegram/check` (`pending | expired | signedIn` + customer); a confirmed token opens a session once (`AuthService.openSession`, shared with SMS sign-in) — the same account as by SMS on that number.
- Personal data (`customers/account.service.ts`, rules in the pure, unit-tested `customers/account-erasure.ts`): `GET /me/export` → `AccountExport` (profile, bookings, own reviews and questions, loyalty per place, certificates on the number, online subscription orders, fiscal receipts of own visits, waitlist, «Мой мастер», push devices (web and Expo), Telegram links, referrals; no tokens, hashes or other people's data; the web adds the device's hearted services as `deviceFavorites` and saves `awaisa-<date>.json`). `DELETE /me` → `AccountDeleted` (409 while the account is a business's only owner): visits ahead on its number are cancelled the usual client way (the place hears after the undo window, deposits follow the refund rule; visits booked for someone else stay), waitlist entries are cancelled, reviews stay with the places but get `anonymized_at` and «Клиент» (no `authorId`, face or wreath; the reviewer page, the profile and client ranks leave them out), questions are signed «Клиент», bookings and online subscription orders stay in the businesses' books with `customer_id` cleared (fiscal receipts, certificates and loyalty by phone stay too: tax and money records) (their phone and name are the place's records), client and business Telegram links, Telegram sign-ins, referrals and codes are deleted, the customer row goes (sessions, push subscriptions, memberships cascade), the avatar file is removed and `catalog` bumped; the web refreshes the returned `slugs`. On `/bookings` «Настройки» it is «Ваши данные · Скачать мои данные» and, last, a `HoldButton` «Удалить аккаунт» with one footnote of what happens.
- Guards: `AuthGuard`, `OptionalAuthGuard` (booking creation links the booking to the signed-in customer and uses their verified phone), `AdminGuard` (`ADMIN_PHONES`). `@CurrentCustomer()` reads the customer.
- Profile: `POST|DELETE /me/avatar` (`src/media/me-avatar.controller.ts`, multipart `file` → 480² WebP under `customers/`, `customers.avatar_url`, returned as `avatarUrl` in the customer view), `GET|PATCH /me` (`GET` adds `businesses` — slug, name, role of each membership — and `masterOf` — places where the number is an active master — for the profile's cabinet shortcut, the tab bar and the header), `GET /me/bookings`, `DELETE /me/bookings/:id`.
- Schedule (`/manage/:slug/…`): masters, bookings with phones and comments, time off; cancelling texts the client. Time off is subtracted from availability like a booking; the response lists bookings that fall inside it. `ADMIN_PHONES` are platform admins with access to every business.
- SMS: `SmsService` sends through Twilio's REST API when `SMS_DRIVER=twilio` (or Twilio credentials are present), otherwise logs messages (`SMS to …`) — read codes from the API log in development. Texts live in `notifications/messages.ts` (Cyrillic SMS segments are 70/67 characters). Confirmation goes out on booking unless the client turned it off (`sms_confirmation`), a reminder `reminder_minutes` (60 / 120 / 1440, null = none, default 120) before the visit («сегодня/завтра» in the text) from a 5-minute cron (`RemindersService`, rows claimed with `UPDATE … RETURNING`, safe with several instances), and a notice when the salon cancels. ## Code style

Follows https://react-typescript-style-guide.com/, enforced by Biome where possible:

- Single quotes (JS and JSX), no semicolons, trailing commas.
- Components are arrow functions with named exports: `export const ProfileHero = () => {}`. Default exports only where a framework requires them (Next.js `page`/`layout`, `*.config.ts`).
- `interface` for component props, `type` for everything else.
- Component order: hooks → variables → `useEffect` → handlers → `return`. Early returns over `else`.
- Folders follow FSD segments: `ui/<Name>/<Name>.tsx`, `model/useX.ts`, `lib/`, `api/`, `config/` inside a slice; `shared/{ui,lib,lib/hooks,api,config,styles}`.
- Files: components PascalCase, everything else camelCase. The API keeps Nest naming (`*.module.ts`, `*.controller.ts`).
- Several exports from one file go in a single `export { ... }` at the bottom.
- No comments that restate code; comment only the "why" (workarounds, platform quirks).

## Conventions

- Lint/format: Biome only (root `biome.json`, per-app overrides in `apps/*/biome.json`). No ESLint/Prettier.
- API: Biome `useImportType` is off — Nest DI needs runtime imports for constructor-injected classes.
- API DB: entities are `*.entity.ts` (auto-loaded), `synchronize` is off. Schema changes go through migrations:
  `pnpm --filter api migration:generate` → `pnpm --filter api migration:run`. Migrations also run on API start.
- Env: `.env` at repo root (copy from `.env.example`), validated by `apps/api/src/config/env.ts`. Mobile reads `apps/mobile/.env` (`EXPO_PUBLIC_WEB_URL`).
