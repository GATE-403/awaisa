# AGENTS.md

Turborepo monorepo, pnpm workspaces.

- `apps/web` — Next.js (App Router, `src/`, Cache Components, React Compiler). Read `apps/web/AGENTS.md` before editing it.
- `apps/api` — NestJS (ESM) + TypeORM + PostgreSQL. Read `apps/api/AGENTS.md` before editing it.
- `apps/mobile` — Expo (SDK 58) shell that renders `apps/web` in a WebView. Read `apps/mobile/AGENTS.md` before editing it.
- `packages/tokens` — design tokens (colors light/dark, spacing, radius, typography, durations) as TS. `build` generates `dist/tokens.css` (CSS variables). Used by web (CSS) and mobile (JS).
- `packages/ui` — in-house UI kit for web: Base UI (`@base-ui/react`) primitives styled with CSS Modules on token variables, shadcn-style (source lives here, not on npm).

## UI kit

- Import per component: `import { Button } from '@awaisa/ui/Button'`. Global styles: `@awaisa/ui/styles.css` + `@awaisa/tokens/tokens.css` (imported in `apps/web/src/app/layout.tsx`).
- New component: `packages/ui/src/components/<Name>/{<Name>.tsx, <Name>.module.css, index.ts}`. Wrap the Base UI part, merge `className` with `mergeClassName`, expose variants as `data-*` attributes and style them in CSS.
- Style states via Base UI data attributes (`data-checked`, `data-open`, `data-disabled`, `data-invalid`, `data-starting-style`/`data-ending-style` for animations). Docs: https://base-ui.com/react/overview/quick-start
- Only CSS variables from tokens — no hard-coded colors/sizes. Theme: system by default, force with `<html data-theme='light' | 'dark'>`.
- Base UI is DOM-only, so `packages/ui` does not work in React Native. For native screens, add `packages/ui-native` with the same component API on RN primitives and the same tokens.
- Demo of all components: `/ui` in the web app.
- Components: Menu (`@awaisa/ui/Menu`: `Menu` + `MenuItem` (`variant='danger'`, trailing `icon`) — an iOS pull-down menu by its button; use it instead of a sheet for two or three actions). Input and Select also have `variant='plain'` (borderless, right-aligned value for Settings-style rows). Button (primary/secondary/outline/ghost/danger/link/contrast × sm/md/lg), ButtonLink (navigation styled as a button — use it instead of `Button render={<a>}`, which gets `role="button"`), Link (renders Next `<Link>` via `render`), Input, Field, Select, Checkbox (incl. indeterminate), Switch, Radio + RadioGroup, RadioCard, Tabs, Dialog, Skeleton. The set follows the Figma file `Awaisa` (Components section); colors, typography and sizes come from tokens, not from Figma.

## Design system (macOS / iOS principles)

The look follows Apple HIG and the restrained style of apple.com: depth through layers, not borders.

- Layers: page `--color-background` (grouped gray #F2F2F7 / black) → content cards `--color-surface` (white / #1C1C1E) with `--shadow-sm` → floating chrome in matte material `--color-material` + `backdrop-filter: var(--blur-material)` + 0.5px `--color-material-border`. Do not put borders around cards.
- Values come from Apple's macOS 26 UI kit (Figma «macOS 26 (Community)»): system accents (blue #0088ff/#0091ff, red #ff383c/#ff4245, …), label/fill alphas (fills 8–10%, tertiary label 25%), Thick material (#f6f6f6 72%, blur 30) and the 590 «emphasized» semibold. Text-carrying fills (`primary` #0071e3, `link`, `muted-foreground`) stay darker for AA.
- Colors are Apple semantic colors: `foreground` (label), `muted-foreground` (secondaryLabel, slightly darker for AA), `tertiary-foreground`, `subtle` (system fill), `border` (separator, use 0.5px hairlines), system blue/green/red/orange as `primary`/`success`/`danger`/`rating`. Never use palette values in components.
- Type: SF Pro (Text and Display) on Apple devices, Inter elsewhere — no other web fonts (`--font-sans` / `--font-display`). One body size everywhere: `--text-body` 15 for rows, sheets, forms and lists (catalog density), `--text-input` 16 in text fields (iOS does not zoom from 16), `--text-footnote` 13 for secondary text, `--text-xs` 12 captions. Headings step down clearly: `--text-title1` 28 page titles (34 from 768px), `--text-title2` 22 section titles (bold), `--text-title3` 17 group/card/step titles (semibold), uppercase 13 group captions. Titles have negative tracking (`--tracking-tight` / `--tracking-title`).
- Shapes: every one-line control — buttons, fields, selects, search, chips, tab bar, segmented controls — is a capsule (`--radius-control` / `--radius-full`); only containers are rounded rects (cards 16–22, sheets 28, menus 12). Multi-line text areas keep 12. Touch targets ≥ 44px (`--control-height-md`).
- Patterns: Settings-style inset grouped lists (`RadioGroup variant=inset`, uppercase footnote section headers, hairline separators inset 16px, value/chevron on the right), checkmark instead of radio circles in lists, segmented `Tabs`, iOS green switches, floating material tab bar and action bar on phones.
- Icons: Phosphor (`@phosphor-icons/react/ssr`) for UI glyphs only (`regular`, `fill` for the active tab, `bold` for chevrons). No decorative icons or illustrations — the look is typographic.
- Look follows apple.com/store: page `#f5f5f7`, text `#1d1d1f`/`#6e6e73`, blue `#0071e3` for fills and `--color-link` `#0066cc` for blue text on gray (AA contrast). Two-tone headings: bold title + muted continuation (`PageTitle`, `StoreShelf`). White cards, radius 28, soft `--shadow-sm`, small uppercase eyebrow (`--color-highlight` for "new/hit").
- Controls follow the macOS 26 kit (Figma «macOS 26 (Community)», Buttons / Segmented Controls): flat capsule push buttons, 510 labels. `primary` = Default (accent `#0a6cf0` fill — the kit's #0D6FFF a hair deeper for AA), `secondary` = Bordered Neutral (`--color-fill` 5%), `outline` = Bordered Secondary (accent at 10%, accent label), `ghost` = Borderless, `danger` = Bordered Destructive (neutral fill, `--color-danger-text`). Segmented controls (`shared/ui/SegmentedControl`) follow macOS 26: a capsule `--color-fill` track, equal segments, 46pt tall (42pt segments in a 2pt track), a raised `--color-elevated` knob with a soft shadow that slides (spring) under the chosen segment, the chosen label semibold in `foreground`, hairlines between unselected neighbours. Time/day toggles are neutral fills, pressed = accent. Page headers use `--text-display` (56/60 bold) from 1024px. Toolbars and sidebars (Titlebars and toolbars / Sidebars pages): from 768px the header's icon buttons sit in one 36pt Liquid Glass capsule (Window/Button Group) next to the 36pt accent «Записаться» capsule; on desktop `/map` the list is a floating sidebar (inset 12, radius 20, material, rows highlighted in place with `--color-fill`, radius 8) over a full-bleed map. `/map` has no site footer. Businesses are shown with `BusinessTile` (app-icon style gradient square, colour picked from the name).
- Layers in dark: page #000 → card `--color-surface` #1C1C1E → sheet rows `--color-sheet-surface` #2C2C2E on `--color-sheet`; each layer up is lighter, so depth shows without shadows.
- Pictures lead: businesses have a cover (catalog card, business page) and up to 6 work photos (`Работы` mosaic); masters have photos (contact-style picker in the master sheet). Without a cover the card shows the tinted `BusinessTile`.
- Restraint: no glow, one primary action per screen, secondary actions as compact `secondary` buttons. No glass/blur effects except the standard material on header, tab bar and booking bar.
- Real-world metaphors: bookings are shown as an e-ticket (`entities/booking/ui/Ticket`: tear-off calendar leaf, perforation with notches, stub with code + barcode; cancelled tickets get an «Отменена» pill, a grey leaf, struck-through time and a faded barcode). Feedback goes through iOS-style toasts (`useToast()` from `@awaisa/ui/Toast`, provider in the root layout): success/error/info; `onOpen` makes the whole toast a tap target that opens what it is about, like a notification («Новая запись» → that day in the schedule with the booking open via `?tab=schedule&date=&booking=`; the system notification does the same).
- Weight: cards rest on the page through layered shadows (`--shadow-sm/md/lg`: a tight contact shadow plus a wide ambient one); material panes (header, cabinet bar, business bar, tab bar, sheet bars) carry a lit top edge (`--shadow-material`, `--color-material-highlight`). Under sticky bars content dims through a scroll edge gradient (`--color-scroll-edge`, `::after`) instead of a hairline; on business pages the business bar carries it. Tracking is size-specific: `--tracking-display` for 48–56px headings, `--tracking-tight`/`title` for titles, `--tracking-caption` for 12–13px labels. `prefers-reduced-transparency` and `prefers-contrast: more` swap glass for solid `--color-sheet` panes (and stronger borders/secondary text) in `tokens.css`.
- Mobile performance: on touch devices that are not iOS (`@supports not (-webkit-touch-callout: none)` + `pointer: coarse`, i.e. Android) `tokens.css` turns `--blur-material` off and makes `--color-material`/`--color-chrome` solid — live blur under sticky bars is recomputed every scrolled frame; view-transition animations are off there too. Never animate layout properties (height, grid rows, top) on scroll; the header's chip row stays put and `--header-height` is written at most once a frame and only on change. Endless animations stop off screen (`OrbitScene` uses an IntersectionObserver). Footer and lower business-page sections use `content-visibility: auto`. `<html data-scroll-behavior='smooth'>` lets Next jump to the top on navigation.
- Material blur: only `backdrop-filter: var(--blur-material)` in source — Lightning CSS adds `-webkit-`. Writing both by hand makes the minifier drop the standard one.
- Motion: `--ease-standard`, `--ease-spring` for toggles/indicators; pressed state = `scale: 0.97`. The catalog card morphs into the business cover with React `<ViewTransition name="business-<slug>">`; phone sheets slide up with a slight settle. Everything is cut by `prefers-reduced-motion`. In the app, `haptic()` (`nativeBridge.ts`) plays taptic feedback (booking done, error, cancel, drag pick-up).
- Reversible actions are not confirmed: cancelling (client or salon) and dragging a booking happen at once with «Вернуть» in the toast (`useToast().show({ action })`); the API keeps a 15 s undo window (`UNDO_WINDOW_SECONDS`, `POST …/restore`) and sends the salon's SMS only after it.
- Inputs format while typing: `maskPhoneInput` (+996 555 123 456) and `maskAmountInput` (1 500) from `shared/lib/inputMasks.ts`; tel/numeric keyboards and `one-time-code`.
- Copy uses verbs and the next action («Добавьте первую услугу», «Запишитесь к мастеру»).
- Less to read: say only what decides the next tap. Phones get one-line meta, smaller titles (`PageTitle` 22px), no decorative headings where tabs already name the view, optional things behind a link («Добавить комментарий», notification settings, the week's hours, reviews past three). Prefer short facts («Сегодня с 15:30») to sentences («Свободно сегодня с 15:30»).
- Spacing on a 4px grid (`--space-1` = 4px … `--space-20` = 80px). Breakpoints (JS only, literal px in media queries): sm 640, md 768, lg 1024, xl 1280.

## Web app structure

The web app is a booking platform: any business registers and gets its own page at `/<slug>`; clients find businesses in the catalog on `/`. Awaisa Studio (`awaisa-studio`) is the first business, migrated from the single-salon version.

- Routes: `/` catalog of businesses (`?kind=`, `?q=`), `/map` places on a map (`?kind=`; «Рядом со мной» sorts by distance), `/<slug>` business page, `/<slug>/services`, `/<slug>/book` booking flow (`?service=` / `?specialist=` / `?branch=` preselect), `/bookings` profile and bookings (`/profile` redirects here), `/login` SMS sign-in (`?next=`), `/review/<bookingId>?s=` rating a visit from the SMS link, `/v/<bookingId>?s=` a visit from the confirmation/reminder SMS (saved on the phone as `sig.<signature>` token, then `/bookings`), `/business` landing for owners, `/business/new` registration, `/manage` my businesses, `/master` → `/master/<slug>` a master's own day, `/manage/<slug>` owner cabinet (`?tab=schedule|clients|analytics|reviews` on top, `services|masters|branches|hours|profile|notifications` under «Настройки» with a second capsule row), `/ui` kit demo. Old `/book`, `/services`, `/admin`, `/profile` redirect to Awaisa Studio / `/manage`.
- A first path segment that isn't an app route is a business slug: keep `APP_SEGMENTS` (`shared/config/navigation.ts`) and `RESERVED_SLUGS` (`apps/api/src/businesses/business-rules.ts`) in sync when adding a top-level route.
- Architecture: Feature-Sliced Design. Layers, each importing only from layers below: `src/app/` (Next routes, layouts — thin files, default exports only here) → `src/views/` (one slice per page: `catalog`, `business`, `services`, `booking`, `bookings` (profile + records), `auth`, `forBusiness`, `manage`, `map`, `review`, `masterDay`; FSD «pages», renamed because Next reserves `pages/`) → `src/widgets/` (`Header`, `HeaderSearch`, `BusinessBar`, `Footer`, `TabBar`, `DayCalendar`, `DayStrip`) → `src/features/` (`theme`, `language`, `favorites`, `addToWallet`, `ticketView`, `bookingAlerts`, `bookingDraft`, `rateVisit`, `rescheduleBooking`, `waitlist`) → `src/entities/` (`business`, `booking`, `offer`, `session`) → `src/shared/` (`api`, `ui`, `lib`, `config`, `styles`). Every slice of views/widgets/features/entities has an `index.ts` public API that exports only what other layers use; import slices through it (`@/entities/booking`), never deep. Entities take features through slots (e.g. `OfferCard action`), not imports. Modules with React hooks carry `'use client'` so barrels stay safe for server components.
- Rendering: pages without data are static (SSG: `/business`, `/login`, `/ui`); every other route is Partial Prerendering — a static shell plus server-streamed data. `'use client'` views are still server-rendered to HTML; what matters is where data is read. Public data is server-rendered from the Cache Components cache (`shared/api/serverApi.ts`: `'use cache'` + `cacheLife('minutes'|'hours')` + `cacheTag('businesses' | 'business:<slug>')`); dynamic parts (search params, slugs) stream into the prerendered shell (Partial Prerendering). After an owner saves in the cabinet, `refreshBusiness(slug)` (server action, `shared/api/revalidate.ts`) calls `updateTag`, so the public page is fresh at once. Personal pages read the session on the server too (`shared/api/sessionApi.ts`, server-only: forwards the request's cookies to the API, `no-store`, always behind `<Suspense>`): `requireCustomer(next)` redirects guests to `/login?next=` before anything renders, `getSessionCustomer()` returns null for guests. `/bookings`, `/manage` (one business → straight to its cabinet), `/manage/<slug>`, `/master` (one place → its day), `/master/<slug>` and `/business/new` pass that customer to `SessionProvider` (`entities/session`, seeds `useSession` so there is no `/api/me` round trip) and the first data as `initial*` props; the client hooks skip their first fetch and refetch after edits. `/review/<id>` is rendered on the server from the SMS signature (`getVisitReviewOnServer`); `/map`'s first list comes from the cache (`listMapPlaces(kind)`), «Рядом со мной» refetches on the client. Live bits stay on the client (next free slots, schedule polling, the places marquee).
- Data: server pages read `getBusiness(slug)` (business + branches + catalog, `notFound()` on 404), `listBusinesses(kind, q)`, `listOffers(kind, q)` and `listPopularServices(kind)`. Dynamic routes pass the `params` promise into `<Suspense>` so the shell stays prerendered. Business data reaches components as props. URL-aware chrome sits in `<Suspense>` in the root layout. Browser calls go through `shared/api/clientApi.ts` to `/api/*`, which `next.config.ts` rewrites to `API_URL` (same origin: no CORS, works in the mobile WebView).
- Coming from outside (2ГИС, Instagram, QR): the cabinet «Филиалы» lists «Ссылки для записи» — one `/<slug>/book?branch=<id>` per branch with «Копировать», so the client lands with their branch chosen. Guests' name and phone are kept after a booking (`entities/booking/lib/contactStorage.ts`, `awaisa:contact:v1`) and filled in next time.
- Client bookings: guests can book without an account; `localStorage` keeps `{ id, token, snapshot }` per booking (`entities/booking/lib/bookingStorage.ts`) and the token lets them view/cancel. Signed-in clients also get the server list (`GET /me/bookings`: their bookings plus any made on their verified number), merged with device bookings on `/bookings`.
- Session on the client: `useSession()` (`entities/session`) (one shared store, fetches `/api/me` once; `status` is `loading | guest | signedIn`), `useRequireSession()` redirects guests to `/login?next=…`. The session is an httpOnly cookie set by the API through the `/api` rewrite — never read it from JS. Booking contacts skip the phone field when signed in. Phones are shown with `formatPhone()`.
- API types are mirrored in `shared/api/types.ts` — keep them in sync with the API responses.

## App shell and responsive rules

- Layout variables live in `src/shared/styles/shell.css`: `--header-height` (56/64), `--tabbar-height` (60 on phones, 0 from 768px), `--page-gutter` (16/24/32), `--section-gap`.
- Footer is apple.com-style: fine print, link columns (Записаться / Для бизнеса / Аккаунт; closed disclosure rows on phones, open columns from 768px via `FooterColumn`), then name, language and theme in one quiet row.
- `/manage` (several businesses) is one Settings-style inset list: a row per business (cover thumb or tile, name with «Открыта/Скрыта» dot, kind · role, the next visit, today's count as a big number on the right; the row opens the cabinet) with a trailing «↗» accessory for the public page (`GET /me/businesses`), then «+ Новая страница».
- Header (`widgets/Header`) is a marketplace header: logo, «Каталог», the search field with live suggestions (`widgets/HeaderSearch`: solid panel, places as you type, «Часто ищут» as a plain list of searches, Enter searches services and places, closes on any outside tap), labelled actions (Карта, Для бизнеса, Записи) from 768px; phones show one row (the mascot and the search field, no submit button) — map and profile live in the tab bar (order Каталог · Карта · Бизнес · Записи). A category row below («Все» first; quiet text chips on phones with only the chosen one on a light fill, text with glyphs from 768px). The header carries a 0.5px hairline under it so it parts from the gray page in light mode. `/bookings` and `/business*` use a slim header without search and categories and «Бишкек · рядом на карте». It publishes its real height as `--header-height`. Business pages add `widgets/BusinessBar` (via `app/[slug]/layout.tsx`): «Каталог › <tile> Бизнес», open status, sections «Обзор · Услуги и цены · Мастера · Контакты», «Записаться» (desktop only — on phones the sections scroll freely and booking lives on the page); one 48px row on phones (`--business-bar-height`).
- Catalog (`/`) is a marketplace: categories live only in the header, «Часто ищут» chips (`GET /businesses/popular-services`, wide screens only), then results with two big text tabs «Места · Услуги» (places first; services first when searching; state resets per query/kind) and a «Сортировка» menu for services; the services feed (`entities/offer` `OfferCard`: 4:3 picture with the favourite heart, name, place · rating, price · length on one line (the price is the one bold thing) and the next free time as blue text («Сегодня с 15:00»); a fire glyph («Хит» for screen readers) marks only the most booked service of each place; the whole card is one stretched link; 2 / 3 / 4 columns at phone / 768 / 1100 and compact `BusinessCard`s (live free time and opening status via one `GET /next-free` through `NextFreeProvider`). Search matches service names too.
- `/<slug>/services` shows services as cards: name, «Хит», description, duration, masters' avatars, price and «Записаться»; a sticky category bar under the business bar.
- `/business` (`views/forBusiness`, static): three-column hero with an interactive CSS 3D scene (`OrbitScene`: the app icon as a thick tile, product chips orbiting; pointer tilts, drag spins with inertia, tap pulses; clipped to its box, sized in `cqi`), a places row (marquee only from 6 places), a panel with the product showcase and a bento of three `TiltCard`s (tilt + glare toward the pointer), stats, steps, FAQ.
- `/book` is a modal screen like a page in Telegram's in-app browser: a sheet (radius 28, slides up) over the site, whose header peeks dimmed and blurred above it (`BookingScrim`, a tap closes); no business bar, tab bar or footer; its own `BookingTopBar` (✕ back to the place, tile, «Запись» over the place name); the sheet scrolls inside itself (`[data-booking-screen]` locks the page) — and its own fixed action bar (phones/tablets) or a sticky summary card (≥1024px); tapping the bar's summary opens a «Ваша запись» sheet with what is chosen. The desktop card's rows (Услуга with its length, Мастер, Когда) are buttons that reopen their step; the first unfinished one reads «Выберите …» in blue. The action button always moves the client to the first unfinished step instead of being disabled.
- Prepayment on the web: the cabinet service sheet has «Предоплата · При записи онлайн, сом» (only when `GET /payments/config` says payments are available; ≤ price; the footer explains the 15-minute hold and the 24-hour refund rule). The booking summary names the deposit before the click; after booking the client goes to `checkoutUrl` (`/pay/<id>`: place, amount, the rest at the salon, «Оплатить N сом», the hold's end time, a test-mode badge) and comes back to `/bookings?paid=` with a toast. An unpaid pass says «Ждёт оплаты» and offers only «Оплатить»; the ticket, the cabinet booking sheet and the calendar block show the deposit's state (`describeDeposit`, `PAYMENT_STATUS_TEXT` in `entities/booking`).
- Waitlist (`features/waitlist`): on a full day the booking form offers «Сообщить, когда освободится» (`WaitlistJoin` in `DateTimePicker fullDayAction`) → a sheet with name and phone (the account's number when signed in) → `POST /waitlist`; guests keep `{ id, token, snapshot }` in `localStorage` (`awaisa:waitlist:v1`). `/bookings` lists «Жду окна» (`WaitlistList`, device + `GET /me/waitlist`): «Сообщим по SMS, если освободится», then «Освободилось 15:30 — записаться ›» straight to that time, × to stop waiting. In the cabinet schedule a day with waiting clients shows «Ждут окна: N» in the toolbar → `WaitlistSheet` (name, service · master, «Ждёт с …» or «SMS отправлено: свободно 15:30», «Записать» opens `NewBookingDialog` prefilled with service, name, phone and the freed time, a call link, × to drop).
- Links carry what they show: `/book?service=&specialist=any&date=&time=` (popular cards, «Ближайшее окно») opens the form on that time and folds to contacts; if the time is gone a toast says so and the client picks another. Catalog offer cards show the place's first free time as «Сегодня с 15:00» and pass only `date`.
- Smart defaults: a service with one master fills the master step (also when a link says «любой мастер»); the suggested day skips ahead (up to 6 open days) when the first open day has no free time; «Снова» in history passes `?service=&specialist=`.
- Booking shows one step at a time: done steps fold to their summary, steps not reached yet show only their title (a «Показать» opens them), the step in progress has no «Свернуть»; the site footer is hidden on `/book`. Booking steps are disclosures: a glyph per step (no numbers; a check when done), the header toggles «Изменить / Свернуть / Показать»; completed steps fold automatically, the client can fold or unfold any step. The contacts step ends with one folded line «SMS-подтверждение · напомним за 2 часа · Изменить» that opens «SMS с подтверждением» (switch) and «Напомнить о визите» (за 1 час / 2 часа / за день / не напоминать); the comment field waits behind «Добавить комментарий» (`smsConfirmation`, `reminderMinutes` on the booking). A half-made booking is kept on the device (`features/bookingDraft`, 24 h) and offered back by a «Продолжить запись» pill above the tab bar on every other page; it is cleared after booking.
- Sheets (`shared/ui/Sheet`) open a frame after mount so they slide up, and slide down before the caller unmounts them (`onOpenChangeComplete`); dialogs sit at z 80+ above page layers. They have an iOS grabber and close when the top bar is pulled down (`useSheetDrag`: > 120px, or where the gesture would coast to — momentum projection with deceleration 0.998 — passes half the sheet; it leaves at the finger's speed; a short pull settles back without overshoot; pulling up rubber-bands).
- Catalog and other filter switches use `shared/ui/SegmentedControl` (native radios styled as the kit's segmented control) where a segmented control fits; result views use text tabs. Anything fixed to the bottom pads for `env(safe-area-inset-bottom)`; while the «Продолжить запись» pill is on screen `--resume-space` (72px) is added to the footer and the `/map` list so it never covers content; the viewport uses `viewport-fit: cover`.
- Never read the current time during render on the server: use `useToday()` (server snapshot is `null`, the client fills it in).
- Business page (`views/business/ui/Place`, one stylesheet `Place.module.css` built on the type scale): a wide cover only when there is a photo (the app-icon tile rests on its edge; without a photo no banner, the tile and name lead), the name in title1, one line of facts («★ 4.4 (206) · Барбершопы»), status with a dot · street on one line (cut, whole on tap via `AddressLine`), the description from 640px. Actions: one primary «Выбрать услугу» capsule and secondary white capsules of the same height with a blue glyph and a verb (Позвонить · Написать · Маршрут · Поделиться; on phones equal tiles with the glyph over the word). ## Booking API (apps/api)

- Public: `GET /businesses?kind&q` (published businesses with at least one active service), `GET /businesses/:slug` (business + catalog), `GET /businesses/slug-available?slug`, `GET /availability?serviceId&specialistId&date[&branchId]`, `GET /map?lat&lng&kind&q` (pinned branches of published businesses, haversine `distanceKm`, nearest first), `GET /next-free?slugs=` (first free time today/tomorrow per business, quickest service, any master), `POST /bookings`, `GET|DELETE /bookings/:id` with `x-booking-token`. `specialistId=any` picks the first free specialist. Service ids are global, so the service decides the business.
- Businesses (`src/businesses`): `businesses`, `business_members` (owner/staff), `working_hours` (weekday 0 = Monday; no row = day off); categories, services, specialists and bookings carry `business_id`. New rows created by owners get UUID ids; new masters have no rating until reviews exist.
- Analytics (`src/admin/analytics.service.ts`): raw SQL aggregates over `bookings` × `services` in business time (UTC+6): totals and the previous period, daily series, top services, masters with load (booked minutes / open minutes from `working_hours`), clients grouped by phone (new = no earlier confirmed visit), weekday × hour heatmap, upcoming visits.
- Owners: `POST /businesses` (signed in; creates the business, owner membership, default hours 10–20 daily, a «Услуги» category and any template `services`), `GET /me/businesses`, and everything under `/manage/:slug` behind `BusinessAccessGuard` (member of the business or a platform admin from `ADMIN_PHONES`): profile `GET|PATCH`, `PUT hours`, categories, services (`PUT` full object; a new service is given to every active master), specialists, `GET schedule?date`, `POST bookings` (staff books a client in: phone required, same slot rules and SMS), `POST|PUT|DELETE branches` (the last branch can't be deleted or closed), `PATCH bookings/:id` (move: date, time, master; time off and overlaps refused, SMS after the undo window), `POST bookings/:id/cancel`, `POST bookings/:id/restore`, `GET bookings/recent?since`, `POST|DELETE time-off`, photos: `POST|DELETE cover`, `POST|DELETE photos`, `POST|DELETE specialists/:id/photo` (multipart `file`, ≤ 10 MB).
- Branches (`branches` table, `src/businesses/branch.entity.ts`): bookings store `branch_id` (the master's branch, else the requested one, else the first); a booking's view uses the branch address and phone. `map` and `review` are reserved slugs.
- Photos (`src/media`): every upload is re-encoded by sharp (EXIF dropped, rotated, capped: cover 1600×1000, photo 1400 wide, avatar 480², WebP q80). `StorageService` writes to S3-compatible storage (Cloudflare R2) when `STORAGE_DRIVER=s3` / `S3_BUCKET` is set, else to `UPLOAD_DIR` served by `GET /media/:folder/:file` (`/api/media/…` from the web).
- Master accounts (`src/master`, `specialists.phone` E.164, set through `PUT /manage/:slug/specialists/:id` `phone`, returned only in the cabinet catalog): `GET /me/master` (places), `GET /master/:slug/day?date` and `PATCH /master/:slug/bookings/:id/outcome` behind `MasterGuard` (signed-in phone = an active master of the business; only their own bookings, others are 403). `master` is a reserved slug.
- Master schedules (`catalog/master-schedule.service.ts`, tables `specialist_hours` (no row = day off) and `specialist_leaves`, `specialists.has_own_hours`): `GET /manage/:slug/specialists/:id/schedule`, `PUT …/hours` (`hasOwnHours`, `days`), `POST|DELETE …/leaves`. A master's off hours and leaves become busy intervals (`master-hours.ts` `offHoursAsBusy`, unit-tested) inside the business window, so `buildSlots`, staff bookings, «любой мастер» and next-free respect them; moving a booking outside them is refused; `GET schedule` gives each master `hours` (null = off), `isOnLeave`, `leaveReason`.
- Signed visit links (`common/visit-link.ts`, unit-tested): `visitLink` = `/v/<id>?s=<HMAC('visit:'+id, AUTH_SECRET)>`, sent in the confirmation («Перенести или отменить»), reminder and reschedule SMS; any `x-booking-token` of the form `sig.<signature>` is accepted wherever the booking token is (view, cancel, restore, move).
- Client moves: `PATCH /bookings/:id` (`date`, `time`; device token or the signed-in owner) keeps the master and service, uses the same slot rules (the booking does not block its own new time), refuses visits that have started, resets the reminder, texts the client (if SMS is on) and tells the owner's Telegram «Клиент перенёс запись». Staff moves into the past are refused. `GET /manage/:slug/bookings/unclosed` lists ended visits without an outcome in the last 30 days per day. `specialists.commission_percent` (0–100) gives analytics masters `percent` and `payout`.
- Visit outcomes: `PATCH /manage/:slug/bookings/:id/outcome` (`outcome` arrived | no_show | null, `paidAmount`, `paymentMethod` cash | card | transfer; only confirmed bookings from their day on) → `bookings.outcome`, `paid_amount`, `payment_method`, `outcome_at`; admin views carry them. Analytics counts a visit unless it was a no-show and earns `COALESCE(paid_amount, price)`; totals add `noShows`, `noShowRate` and `payments` (cash, card, transfer, unmarked).
- Prepayment (`bookings/payments.service.ts`, `payments.controller.ts`, table `payments`; `services.deposit`, `bookings.deposit_amount | payment_status | payment_due_at | cancelled_by`): an online booking of a service with a deposit is created `confirmed` but `payment_status = pending`, holding its slot `PAYMENT_HOLD_MINUTES` (15) while the client pays; its confirmation SMS, reminder and the owner's Telegram wait for the payment. `POST /bookings` then returns `checkoutUrl`. `PAYMENT_DRIVER`: `test` (default outside production) is the built-in checkout — our `/pay/<id>?s=<HMAC('pay:'+id)>` page and `POST /payments/:id/test-complete?s=`; `none` (default in production) turns deposits off; a real acquirer (Freedom Pay, MBANK, O!Деньги…) becomes one more driver: its checkout, webhook and refund. `BookingsService.onPaid` confirms (paid after the hold ran out → refunded). `settlePayments` (every minute) releases unpaid holds (`expired`, booking cancelled, slot free) and, after the undo window, settles deposits of cancelled visits: refunded when the salon cancelled or the client cancelled ≥ `DEPOSIT_REFUND_HOURS` (24) ahead, else `kept`. `GET /payments/config`, `GET /payments/:id?s=`, `GET /bookings/:id/checkout` (token or session). Staff bookings never ask for a deposit. `pay` is a reserved slug.
- Waitlist (`src/waitlist`, table `waitlist_entries`: service, master or null = any, branch, day, name, phone, hashed token, status waiting | notified | cancelled | expired): `POST /waitlist` (OptionalAuth, booking rate limit; refused with 409 when the day has free time; one entry per phone, service, master and day), `GET|DELETE /waitlist/:id` with `x-waitlist-token`, `GET /me/waitlist`, `DELETE /me/waitlist/:id`; the cabinet reads `GET /manage/:slug/waitlist` (upcoming waiting/notified entries with name and phone; anyone who has since booked that day drops off) and `DELETE /manage/:slug/waitlist/:id`. `WaitlistService.notifyFreed` (every minute) expires past days and checks availability per (service, master, branch, day); when a time is free it claims the group (`UPDATE … WHERE status = 'waiting'`) and texts each client one `waitlistFreedMessage` with `/<slug>/book?service=&specialist=&date=&time=`. A cancellation still in its undo window is not counted.
- Clients (`src/clients`, table `client_records`: the business's note and birthday per phone): `GET /manage/:slug/clients?q`, `GET|PUT /manage/:slug/clients/:phone`.
- Reviews (`src/reviews`, table `reviews`, one per booking): `GET|POST /bookings/:id/review` (booking token `x-booking-token`, SMS signature `x-review-signature` or the session; only confirmed visits that have ended), `GET /businesses/:slug/reviews?limit` (count, average, distribution, items; authors shown as «Имя Ф.»), `GET /manage/:slug/reviews`, `PUT /manage/:slug/reviews/:id/reply`. A review recomputes the master's `rating` as the mean of real reviews. `ReviewsService.sendReviewRequests` (10-minute cron, rows claimed via `bookings.review_requested_at`) sends the link.
- Telegram bot for owners (`src/telegram`, tables `telegram_chats`, `telegram_link_codes`): `GET manage/:slug/telegram` (`isAvailable`, chats), `POST …/telegram/link` (15-minute one-time `/start` code), `DELETE …/telegram/:id`, `POST /telegram/webhook` (checked by `X-Telegram-Bot-Api-Secret-Token`). Without `TELEGRAM_WEBHOOK_URL` the API long-polls `getUpdates` (one instance only). Chats get client bookings (staff ones skipped), client cancellations after the undo window, new reviews, and the day's schedule at 9:00 (`0 3 * * *` UTC); commands `/today`, `/stop`. Texts in `telegram/telegram-messages.ts` (HTML, escaped). Without `TELEGRAM_BOT_TOKEN` messages are logged.
- Wallet (`src/wallet`): `GET /wallet/config`, `POST /bookings/:id/wallet` (token) or `/me/bookings/:id/wallet` → short-lived HMAC-signed `/api/wallet/apple/:id` (.pkpass via passkit-generator, needs `WALLET_*` certs) and a «Save to Google Wallet» JWT link (`GOOGLE_WALLET_*`). Buttons appear only when configured.
- Time zone is fixed UTC+6 for every business (`src/common/business-time.ts`). Opening hours and slot step (15/30/60) are per business; lead time, booking horizon and reminder lead are in `src/bookings/booking-rules.ts`.
- Slots are computed by the pure `buildSlots` (`src/bookings/availability.ts`, unit-tested). Double booking is prevented by the Postgres exclusion constraint `bookings_no_overlap` (btree_gist); a violation returns 409 and the web re-fetches slots.
- Validation: Zod schemas in `*.schemas.ts` via `@Body({ schema })` / `@Query({ schema })` + global `StandardSchemaValidationPipe`. Rate limit per IP: `RATE_LIMIT_PER_MINUTE` (120) and `BOOKING_RATE_LIMIT_PER_MINUTE` (5) for `POST /bookings`; `GET /catalog` is not limited because the web server fetches it for every visitor from one IP (`trust proxy` is on for private networks).
- Awaisa Studio's catalog was seeded by the `SeedCatalog` migration and moved into the platform by `Businesses`; other businesses edit their data in the cabinet.

## Accounts, SMS and admin (apps/api)

- Sign-in by phone: `POST /auth/otp` (`channel: auto | sms`) → 6-digit code, sent to Telegram through the Telegram Gateway when `TELEGRAM_GATEWAY_TOKEN` is set (`checkSendAbility` pays, the send with its `request_id` is free, `ttl` refunds undelivered codes) and by SMS otherwise or when Telegram refuses the number; the response says which `channel` was used and the login page offers "Нет Telegram? Получить SMS". The resend cooldown is per channel. The code itself is ours (HMAC-hashed with `AUTH_SECRET`, 5 min, 5 attempts, one per 60 s and 10 per day per number), `POST /auth/verify` → creates the customer if new and sets the `awaisa_session` cookie (opaque token, sha256 in `sessions`, 30 days), `POST /auth/logout`. Phones are normalized to E.164 by `common/phone.ts` (`0555…`/`555…` → `+996555…`).
- Guards: `AuthGuard`, `OptionalAuthGuard` (booking creation links the booking to the signed-in customer and uses their verified phone), `AdminGuard` (`ADMIN_PHONES`). `@CurrentCustomer()` reads the customer.
- Profile: `GET|PATCH /me`, `GET /me/bookings`, `DELETE /me/bookings/:id`.
- Schedule (`/manage/:slug/…`): masters, bookings with phones and comments, time off; cancelling texts the client. Time off is subtracted from availability like a booking; the response lists bookings that fall inside it. `ADMIN_PHONES` are platform admins with access to every business.
- SMS: `SmsService` sends through Twilio's REST API when `SMS_DRIVER=twilio` (or Twilio credentials are present), otherwise logs messages (`SMS to …`) — read codes from the API log in development. Texts live in `notifications/messages.ts` (Cyrillic SMS segments are 70/67 characters). Confirmation goes out on booking unless the client turned it off (`sms_confirmation`), a reminder `reminder_minutes` (60 / 120 / 1440, null = none, default 120) before the visit («сегодня/завтра» in the text) from a 5-minute cron (`RemindersService`, rows claimed with `UPDATE … RETURNING`, safe with several instances), and a notice when the salon cancels. Booking flows never fail because of SMS (`sendSafely`).
- Env (photos, wallet): `STORAGE_DRIVER`, `UPLOAD_DIR`, `S3_BUCKET`, `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_PUBLIC_URL`; `WALLET_PASS_TYPE_ID`, `WALLET_TEAM_ID`, `WALLET_CERT_PEM`, `WALLET_KEY_PEM`, `WALLET_KEY_PASSPHRASE`, `WALLET_WWDR_PEM`, `GOOGLE_WALLET_ISSUER_ID`, `GOOGLE_WALLET_SERVICE_ACCOUNT` (PEM/JSON raw or base64).
- Env: `AUTH_SECRET` (required in production, ≥ 32 chars), `ADMIN_PHONES`, `PUBLIC_WEB_URL` (links in SMS), `SMS_DRIVER`, `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM` or `TWILIO_MESSAGING_SERVICE_SID`, `TELEGRAM_GATEWAY_TOKEN`, `AUTH_RATE_LIMIT_PER_MINUTE`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` (turns the cabinet section on), `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_WEBHOOK_URL`. `OTP_TEST_CODE` fixes the code and drops the per-number limits for tests; it is rejected in production.

## Mobile ↔ web bridge

- The WebView loads `EXPO_PUBLIC_WEB_URL` (in `apps/mobile/.env`), or in dev `http://<dev machine LAN IP>:3000`.
- Before the page loads, the shell sets `window.__NATIVE_APP__ = { platform, version }`.
- Web → native: `postToNative()` (`openExternal`, `haptic` → expo-haptics) from `apps/web/src/shared/lib/nativeBridge.ts`. Message types are mirrored in `apps/mobile/src/common/utils/nativeBridge.ts` — change both together.
- Links to other origins open in the system browser; Android back navigates the web history first.
- `allowedDevOrigins` in `apps/web/next.config.ts` lets the phone reach the Next dev server by LAN IP.

## Code style

Follows https://react-typescript-style-guide.com/, enforced by Biome where possible:

- Single quotes (JS and JSX), no semicolons, trailing commas.
- Components are arrow functions with named exports: `export const ProfileHero = () => {}`. Default exports only where a framework requires them (Next.js `page`/`layout`, `*.config.ts`).
- `interface` for component props, `type` for everything else.
- Component order: hooks → variables → `useEffect` → handlers → `return`. Early returns over `else`.
- Folders follow FSD segments: `ui/<Name>/<Name>.tsx`, `model/useX.ts`, `lib/`, `api/`, `config/` inside a slice; `shared/{ui,lib,lib/hooks,api,config,styles}`.
- Files: components PascalCase, everything else camelCase. The API keeps Nest naming (`*.module.ts`, `*.controller.ts`).
- Several exports from one file go in a single `export { ... }` at the bottom.
- No comments that restate code; comment only the "why" (workarounds, platform quirks).

## Conventions

- Lint/format: Biome only (root `biome.json`, per-app overrides in `apps/*/biome.json`). No ESLint/Prettier.
- API: Biome `useImportType` is off — Nest DI needs runtime imports for constructor-injected classes.
- API DB: entities are `*.entity.ts` (auto-loaded), `synchronize` is off. Schema changes go through migrations:
  `pnpm --filter api migration:generate` → `pnpm --filter api migration:run`. Migrations also run on API start.
- Env: `.env` at repo root (copy from `.env.example`), validated by `apps/api/src/config/env.ts`. Mobile reads `apps/mobile/.env` (`EXPO_PUBLIC_WEB_URL`).

## E2E, UX and cognitive-load tests

`apps/web/e2e` (Playwright + axe, projects `mobile` = Pixel 7 and `desktop` = 1440×900). The config starts its own API on :4210 (raised rate limits) and web on :3210, so dev servers on 3000/4000 are untouched. First run: `pnpm --filter web exec playwright install chromium`.

- `booking-flow.spec.ts` — real user journeys against the API: home → next slot → book, full booking → ticket (show the ticket alone, close it by pulling the sheet down) → cancel with undo, master and catalog deep links, continuing a half-made booking from another page. Bookings it creates are cancelled afterwards (customer name `E2E Тест`).
- `platform.spec.ts` — an owner registers a business (auto slug, availability check, kind templates), adds a second branch, uploads a cover, adds a service and a master, a guest finds it in the catalog and books, the owner sees the booking, books a walk-in by tapping an empty slot and drags it (desktop) with undo; reserved/taken slugs are refused; closed days are disabled.
- `account.spec.ts` — SMS sign-in (new client names themselves, wrong code shows attempts left, `/profile` lands on the merged profile page with a sign-in card), signed-in booking without a phone field visible from another device, staff schedule: non-staff blocked, close/reopen time, cancel a client's booking. The e2e API runs with `OTP_TEST_CODE=111111` and test staff numbers.
- `ux.spec.ts` — the main action is never disabled and jumps to the first unfinished step, stays on screen on phones, no validation before the first submit, inline errors keep input, 409 conflict and slot-loading failures recover, collapsed steps reopen, success screen offers next steps, no horizontal scroll at 320–1024px, tap targets ≥ 44px, keyboard-only booking. API errors are mocked with `page.route`.
- `cognitive-load.spec.ts` — budgets: ≤ 4 steps with ≤ 3-word titles, ≤ 9 options per decision, ≤ 20 words before the first choice, ≤ 2 required fields, happy path ≤ 7 actions, price/duration visible before committing, ≤ 1 primary button on screen, a hint always names the next action. Change `LIMITS` only deliberately.
- `map.spec.ts` — `/map` lists pinned places, books at the chosen branch, sorts by distance with a granted geolocation, filters by kind.
- `analytics.spec.ts` — the owner reads the report (7-day series, totals, masters), switches the period; other accounts get 403, unsupported periods 400.
- `visit-link.spec.ts` — the SMS link saves the visit on the phone and it can be cancelled; a wrong signature opens nothing; a returning guest's name and phone are filled in; branches have booking links.
- `prepayment.spec.ts` — a service gets a deposit; a guest books through the form, lands on the test checkout, pays and the booking is paid; an unpaid API booking holds its slot until its hold is moved into the past, then the minute cron releases it (desktop only — it changes a service).
- `waitlist.spec.ts` — a free day refuses the waitlist (409); a master's leave fills a day, a guest joins from the form, the leave is removed and the minute cron marks the entry notified; the owner sees them under «Ждут окна» and «Записать» prefills the new booking; «Жду окна» in the profile links to the freed time and can be dropped (desktop only — it changes a master's days).
- `reschedule.spec.ts` — a guest moves a booking from the ticket menu to another time; a wrong token gets 404 and a past visit 400.
- `master.spec.ts` — the owner links a number to a master; that number sees `/me/master`, its own bookings only, closes its own visit and is refused another master's; `/master` lands on the day page; an unlinked number gets 403. The master's phone is restored afterwards.
- `master-schedule.spec.ts` — own hours limit slots to them, a weekday left out is a day off, a leave empties the day and shows in the schedule, the cabinet sheet switches to own hours; the master is restored afterwards.
- `clients.spec.ts` — staff mark one past visit paid by card and another a no-show; the card adds them up; a future visit cannot be marked; search finds the client, the sheet shows the no-show and payment and keeps a note. Past visits come from `e2e/visits.ts` (a real booking moved back in the database).
- `reviews.spec.ts` — a visit moved into the past is rated from the signed SMS link (no stars → inline hint, one review per visit), shows on the business page, the owner replies; a wrong signature opens nothing; the owner links a Telegram chat via a simulated `/start` webhook and unlinks it. It restores the master's rating afterwards.
- `a11y.spec.ts` — no serious/critical axe violations (WCAG 2.1 AA) on every page.
- Test data (bookings, businesses, customers) is named `E2E …` and deleted by `e2e/globalTeardown.ts` after the run (uses `DATABASE_URL` from the root `.env`).
