# AGENTS.md

Turborepo monorepo, pnpm workspaces.

- `apps/web` — Next.js (App Router, `src/`, Cache Components, React Compiler). Read `apps/web/AGENTS.md` before editing it.
- `apps/api` — NestJS (ESM) + TypeORM + PostgreSQL. Read `apps/api/AGENTS.md` before editing it.
- `apps/mobile` — Expo (SDK 58) shell that renders `apps/web` in a WebView. Read `apps/mobile/AGENTS.md` before editing it.
- `packages/tokens` — design tokens (colors light/dark, spacing, radius, typography, durations) as TS. `build` generates `dist/tokens.css` (CSS variables). Used by web (CSS) and mobile (JS).
- `packages/contracts` — the API's request and response types, shared by `apps/api` (type imports only) and `apps/web`.
- `packages/ui` — in-house UI kit for web: Base UI (`@base-ui/react`) primitives styled with CSS Modules on token variables, shadcn-style (source lives here, not on npm).

## UI kit

- Import per component: `import { Button } from '@awaisa/ui/Button'`. Global styles: `@awaisa/ui/styles.css` + `@awaisa/tokens/tokens.css` (imported in `apps/web/src/app/layout.tsx`).
- New component: `packages/ui/src/components/<Name>/{<Name>.tsx, <Name>.module.css, index.ts}`. Wrap the Base UI part, merge `className` with `mergeClassName`, expose variants as `data-*` attributes and style them in CSS.
- Style states via Base UI data attributes (`data-checked`, `data-open`, `data-disabled`, `data-invalid`, `data-starting-style`/`data-ending-style` for animations). Docs: https://base-ui.com/react/overview/quick-start
- Only CSS variables from tokens — no hard-coded colors/sizes. Theme: system by default, force with `<html data-theme='light' | 'dark'>`.
- Base UI is DOM-only, so `packages/ui` does not work in React Native. For native screens, add `packages/ui-native` with the same component API on RN primitives and the same tokens.
- Demo of all components: `/ui` in the web app.
- Components: Menu (`@awaisa/ui/Menu`: `Menu` + `MenuItem` (`variant='danger'`, trailing `icon`) — an iOS pull-down menu by its button; use it instead of a sheet for two or three actions). Input and Select also have `variant='plain'` (borderless, right-aligned value for Settings-style rows). Button (primary/secondary/outline/ghost/danger/link/contrast × sm/md/lg), ButtonLink (navigation styled as a button — use it instead of `Button render={<a>}`, which gets `role="button"`), Link (renders Next `<Link>` via `render`), Input, Field, Select, Checkbox (incl. indeterminate), Switch, Radio + RadioGroup, RadioCard, Tabs, Dialog, Skeleton. The set follows the Figma file `Awaisa` (Components section); colors, typography and sizes come from tokens, not from Figma.

## Design system (macOS / iOS principles)

The look follows Apple HIG and the restrained style of apple.com: depth through layers, not borders.

- Layers: page `--color-background` (grouped gray #F2F2F7 / black) → content cards `--color-surface` (white / #1C1C1E) with `--shadow-sm` → floating chrome in matte material `--color-material` + `backdrop-filter: var(--blur-material)` + 0.5px `--color-material-border`. Do not put borders around cards.
- Values come from Apple's macOS 26 UI kit (Figma «macOS 26 (Community)»): system accents (blue #0088ff/#0091ff, red #ff383c/#ff4245, …), label/fill alphas (fills 8–10%, tertiary label 25%), Thick material (#f6f6f6 72%, blur 30) and the 590 «emphasized» semibold. Text-carrying fills (`primary` #0071e3, `link`, `muted-foreground`) stay darker for AA.
- Colors are Apple semantic colors: `foreground` (label), `muted-foreground` (secondaryLabel, slightly darker for AA), `tertiary-foreground`, `subtle` (system fill), `border` (separator, use 0.5px hairlines), system blue/green/red/orange as `primary`/`success`/`danger`/`rating`. Never use palette values in components.
- Type: SF Pro (Text and Display) on Apple devices, Inter elsewhere — no other web fonts (`--font-sans` / `--font-display`). One body size everywhere: `--text-body` 15 for rows, sheets, forms and lists (catalog density), `--text-input` 16 in text fields (iOS does not zoom from 16), `--text-footnote` 13 for secondary text, `--text-xs` 12 captions. Headings step down clearly: `--text-title1` 28 page titles (34 from 768px), `--text-title2` 22 section titles (bold), `--text-title3` 17 group/card/step titles (semibold), uppercase 13 group captions. Titles have negative tracking (`--tracking-tight` / `--tracking-title`).
- Shapes: every one-line control — buttons, fields, selects, search, chips, tab bar, segmented controls — is a capsule (`--radius-control` / `--radius-full`); only containers are rounded rects (cards 16–22, sheets 28, menus 12). Multi-line text areas keep 12. Touch targets ≥ 44px (`--control-height-md`).
- Patterns: Settings-style inset grouped lists (`RadioGroup variant=inset`, uppercase footnote section headers, hairline separators inset 16px, value/chevron on the right), checkmark instead of radio circles in lists, segmented `Tabs`, iOS green switches, floating material tab bar and action bar on phones.
- Icons: Phosphor (`@phosphor-icons/react/ssr`) for UI glyphs only (`regular`, `fill` for the active tab, `bold` for chevrons). No decorative icons or illustrations — the look is typographic.
- Look follows apple.com/store: page `#f5f5f7`, text `#1d1d1f`/`#6e6e73`, blue `#0071e3` for fills and `--color-link` `#0066cc` for blue text on gray (AA contrast). Two-tone headings: bold title + muted continuation (`PageTitle`, `StoreShelf`). White cards, radius 28, soft `--shadow-sm`, small uppercase eyebrow (`--color-highlight` for "new/hit").
- Controls follow the macOS 26 kit (Figma «macOS 26 (Community)», Buttons / Segmented Controls): flat capsule push buttons, 510 labels. `primary` = Default (accent `#0a6cf0` fill — the kit's #0D6FFF a hair deeper for AA), `secondary` = Bordered Neutral (`--color-fill` 5%), `outline` = Bordered Secondary (accent at 10%, accent label), `ghost` = Borderless, `danger` = Bordered Destructive (neutral fill, `--color-danger-text`). Segmented controls (`shared/ui/SegmentedControl`) follow macOS 26: a capsule `--color-fill` track, equal segments, 46pt tall (42pt segments in a 2pt track), a raised `--color-elevated` knob with a soft shadow that slides (spring) under the chosen segment, the chosen label semibold in `foreground`, hairlines between unselected neighbours. Time/day toggles are neutral fills, pressed = accent. Page headers use `--text-display` (56/60 bold) from 1024px. Toolbars and sidebars (Titlebars and toolbars / Sidebars pages): from 768px the header's icon buttons sit in one 36pt Liquid Glass capsule (Window/Button Group) next to the 36pt accent «Записаться» capsule; on desktop `/map` the list is a floating sidebar (inset 12, radius 20, material, rows highlighted in place with `--color-fill`, radius 8) over a full-bleed map. `/map` has no site footer. Businesses are shown with `BusinessTile` (the owner's logo when there is one — `logoUrl`, uploaded in «Профиль → Фото» through `POST|DELETE /manage/:slug/logo`, 512² WebP, `businesses.logo_url`, on a white plate in the circle; otherwise, logos and faces are circles: a see-through tinted circle: the colour picked from the name as a 16% wash with a tinted hairline and initials in that colour; frosted white on the vivid no-cover cards).
- Layers in dark: page #000 → card `--color-surface` #1C1C1E → sheet rows `--color-sheet-surface` #2C2C2E on `--color-sheet`; each layer up is lighter, so depth shows without shadows.
- Pictures lead: businesses have a cover (catalog card, business page) and up to 30 work photos tagged with service and master (`Работы` mosaic of the first five, the «Работы» feed); masters have photos (contact-style picker in the master sheet). Without a cover the card shows the tinted `BusinessTile`.
- Restraint: no glow, one primary action per screen, secondary actions as compact `secondary` buttons. No glass/blur effects except the standard material on header, tab bar and booking bar.
- Real-world metaphors: bookings are shown as an e-ticket (`entities/booking/ui/Ticket`: tear-off calendar leaf, perforation with notches, stub with code + barcode; cancelled tickets get an «Отменена» pill, a grey leaf, struck-through time and a faded barcode). Feedback goes through iOS-style toasts (`useToast()` from `@awaisa/ui/Toast`, provider in the root layout): success/error/info; `onOpen` makes the whole toast a tap target that opens what it is about, like a notification («Новая запись» → that day in the schedule with the booking open via `?tab=schedule&date=&booking=`; the system notification does the same).
- Weight: cards rest on the page through layered shadows (`--shadow-sm/md/lg`: a tight contact shadow plus a wide ambient one); material panes (header, cabinet bar, business bar, tab bar, sheet bars) carry a lit top edge (`--shadow-material`, `--color-material-highlight`). Under sticky bars content dims through a scroll edge gradient (`--color-scroll-edge`, `::after`) instead of a hairline; on business pages the business bar carries it. Tracking is size-specific: `--tracking-display` for 48–56px headings, `--tracking-tight`/`title` for titles, `--tracking-caption` for 12–13px labels. `prefers-reduced-transparency` and `prefers-contrast: more` swap glass for solid `--color-sheet` panes (and stronger borders/secondary text) in `tokens.css`.
- Mobile performance: no `backdrop-filter` on things repeated per card or over a scrolling feed (favourite heart, hit mark, play mark, tiles, feed chips) — solid or semi-opaque fills instead; blur stays on the few fixed bars. Catalog grids skip off-screen cards with `content-visibility: auto`. Hotlinked CDN pictures are asked for at their shown size with a 2x `srcSet` (`shared/lib/imageSizes.ts` `sizedImage`); catalog cards (`OfferCard`, `BusinessCard`) use `gridImage` — widths 240–840 with the grid's `sizes` (50vw / 33vw / 300px) — which cut the phone catalog's first-screen images from ~1 MB to ~0.6 MB. No virtual list: measured on a production build at 4× CPU slowdown the catalog keeps 60 fps with 72 cards (~2 100 nodes) thanks to `content-visibility`; `next dev` ships ~7 MB of JS against ~1.2 MB, so phone tests over Wi-Fi must use `pnpm build && pnpm start`. Judge speed on a production build (`pnpm build`), not `next dev`.
- Mobile performance (blur): on touch devices that are not iOS (`@supports not (-webkit-touch-callout: none)` + `pointer: coarse`, i.e. Android) `tokens.css` turns `--blur-material` off and makes `--color-material`/`--color-chrome` solid — live blur under sticky bars is recomputed every scrolled frame; view-transition animations are off there too. Never animate layout properties (height, grid rows, top) on scroll; the header's chip row stays put and `--header-height` is written at most once a frame and only on change. Endless animations stop off screen (`OrbitScene` uses an IntersectionObserver). Footer and lower business-page sections use `content-visibility: auto`. `<html data-scroll-behavior='smooth'>` lets Next jump to the top on navigation.
- Loading skeletons mirror the page they stand for: build them from that page's own CSS classes with `shared/ui/Placeholder` — `TextLine` (a bar inside the real heading or paragraph class, so the line keeps its height, also in flex rows), `Picture` (a picture frame) and `Block` (capsules, circles) — static headings stay as real text («Для вас», «Услуги и цены»). Each page skeleton carries `data-page-skeleton` (at least a screen tall, so the footer never shows and then jumps): `CatalogSkeleton`, `PlaceSkeleton` + `BusinessBarSkeleton` (the `[slug]` layout), `ServicesSkeleton`, `LeaderboardSkeleton`, `ProfileSkeleton`; private pages keep `PageSkeleton`. `/book` keeps its fallback — a second sheet would replay the slide-up. Picture frames (`data-picture-frame`: catalog and «Для вас» cards, places, «Работы мастеров», masters, the place cover) show a quiet fill with the mascot (`--color-placeholder-mark`) until the photo is decoded; the frame's tint is only for places and people without a picture.
- One component per pattern (keep using these, don't hand-roll new ones): people's faces are `PersonAvatar` (`entities/business`: the photo or initials on the person's own tint — clients, masters, team, reviewers), places are `BusinessTile`; reviews are `ReviewItem` + `Stars` (`entities/review`, the thread look on the business page and in the cabinet, which adds the phone and visit as `meta` and «Ответить / Изменить» as `replyAction`); tabs are `TextTabs` (no rule under them — only the chosen one is underlined; links, or buttons with `onSelect` for local state, `count`, `size='lg'` for a page's main switch — catalog «Места · Услуги», profile «Предстоящие · История», cabinet, map kinds); filter chips use `shared/ui/Chip/Chip.module.css` (`chip`, `count`; business menu, services page, «Часто ищут»); long lists use `MoreFade` (`shared/ui/MoreFade`: the last item fades, «Ещё N …» floats on the fade, «Скрыть» folds it back and stays floating at the bottom of the screen (sticky) while the open list is in view; reviews, upcoming visits, history).
- Speed on phones: the business cover is a width-based `srcSet` (`fluidImage`); edge-fade masks on sideways rows only apply with a mouse (a mask over a scrolling row repaints every frame on phones); popular service cards take their free time from the place's one `next-free` answer instead of a request per card; `optimizePackageImports` covers Phosphor and Base UI. Check speed on `pnpm build && pnpm start`, not `next dev` over Wi-Fi.
- Visited routes stay in the DOM (Cache Components keeps them hidden with React Activity): never style the shell with `:root:has([data-…])` / `html:has(…)` for something a route renders — it keeps matching on every later page (this once locked scrolling everywhere after `/book`). Set it from an effect instead, which Activity cleans up when it hides the route: `usePageScrollLock()`, `useRootFlag('business-bar')` → `:root[data-business-bar]`. Shell-level parts in the root layout (header, tab bar, «Продолжить запись») are fine.
- Material blur: only `backdrop-filter: var(--blur-material)` in source — Lightning CSS adds `-webkit-`. Writing both by hand makes the minifier drop the standard one.
- Motion: `--ease-standard`, `--ease-spring` for toggles/indicators; pressed state = `scale: 0.97`. Picture cards (offers, places, «Для вас», «Работы мастеров», masters, the master picker) carry `data-card` and their picture `data-card-media`: one rule in `shell.css` — with a mouse the picture zooms slowly (1.06) inside its frame and the shadow deepens, a press sinks the card (0.97, 80 ms) on touch too; no lift, which sideways shelves would clip; the offer card's «Записаться» turns accent on hover. The catalog card morphs into the business cover with React `<ViewTransition name="business-<slug>">`; phone sheets slide up with a slight settle. Everything is cut by `prefers-reduced-motion`. In the app, `haptic()` (`nativeBridge.ts`) plays taptic feedback (booking done, error, cancel, drag pick-up).
- Reversible actions are not confirmed: cancelling (client or salon) and dragging a booking happen at once with «Вернуть» in the toast (`useToast().show({ action })`); the API keeps a 15 s undo window (`UNDO_WINDOW_SECONDS`, `POST …/restore`) and sends the salon's SMS only after it.
- Inputs format while typing: `maskPhoneInput` (+996 555 123 456) and `maskAmountInput` (1 500) from `shared/lib/inputMasks.ts`; tel/numeric keyboards and `one-time-code`.
- Copy uses verbs and the next action («Добавьте первую услугу», «Запишитесь к мастеру»).
- Less to read: say only what decides the next tap. Phones get one-line meta, smaller titles (`PageTitle` 22px), no decorative headings where tabs already name the view, optional things behind a link («Добавить комментарий», notification settings, the week's hours, reviews past three). Prefer short facts («Сегодня с 15:30») to sentences («Свободно сегодня с 15:30»).
- Spacing on a 4px grid (`--space-1` = 4px … `--space-20` = 80px). Breakpoints (JS only, literal px in media queries): sm 640, md 768, lg 1024, xl 1280.

## Design taste (the owner's decisions — follow them)

Rules the owner set after rejecting designs. They apply to every new screen.

- No cheap UI. A «Ближайшее время» card made of a surface card, a tinted glyph in a circle, a title over a subtitle and three wide equal capsules with the day stacked over the time was rejected as «очень дешево, никогда не делай такой дизайн». «Для вас» redone as white row cards (a 64px thumbnail, a reason line, name, price · place) with ‹ › paddles was rejected the same way. Both read like generic templates and list UIs, not the app's picture-led catalog.
  - New blocks start from what the app already has: the kit's `Button` capsules, Settings-style inset rows, footnote captions. Use content-width one-line capsules, not stretched grids. No icon unless it is a UI glyph.
  - Picture shelves keep their 3:4 picture cards. To save space, trim spacing or the card size, never swap them for thumbnail row cards.
  - When a request is about size or space, change the spacing first and ask before redesigning the component.
- Quiet profile style (approved: «да так гораздо лучше запомни этот стиль»), the default for profile-like and content pages:
  - One centred column (~640px) right on the page background. No separate cards per section and no big banners.
  - A soft radial wash of the person's or place's colour behind the head. The face is centred: name in title1, status, then one footnote line of facts with bold numbers.
  - Secondary facts (level, dates) are a single footnote line in the accent colour, not rings or progress widgets. Small secondary capsule actions.
  - Sections under iOS-Settings-style uppercase footnote captions with the count on the right.
  - Collections stay compact: small round faces with first names (≤ 6), capsules with logo and count (≤ 4), reviews as a hairline thread of three with the rest behind `MoreFade`.
  - Gamification is colourful but restrained, like 2GIS: each achievement has its own system colour, earned ones are lit like a coin, unearned ones are grey with «2 из 5» and a thin progress line.
  - A gradient banner with an avatar ring was rejected as «дефолтный шаблон ИИ». A photo-led profile (full-width photo melting into blur, big numbers, two-column desktop) was built and rolled back («убого» on desktop). Do not bring back a photo hero, banners or avatar rings unless asked. Even then, show a mockup or ask first, and never just blow up the phone layout on desktop.

## Web app structure

The web app is a booking platform: any business registers and gets its own page at `/<slug>`; clients find businesses in the catalog on `/`. Awaisa Studio (`awaisa-studio`) is the first business, migrated from the single-salon version.

- Routes: `/` catalog of businesses (`?kind=`, `?q=`), `/feed` «Работы» — a vertical feed of work photos (`?kind=`, `?business=`, `?start=<photo id>`), `/map` places on a map (`?kind=`; «Рядом со мной» sorts by distance), `/<slug>` business page, `/<slug>/services`, `/<slug>/book` booking flow (`?service=` / `?specialist=` / `?branch=` preselect), `/bookings` profile and bookings (`/profile` redirects here), `/login` SMS sign-in (`?next=`, kept only when it resolves to this origin — `shared/lib/safeRedirect.ts`; a prefix check let «/\evil.com» through), `/review/<bookingId>?s=` rating a visit from the SMS link, `/u/<id>` a client's public profile, `/top` the masters' leaderboard (`?kind=`, barbers by default), `/v/<bookingId>?s=` a visit from the confirmation/reminder SMS (saved on the phone as `sig.<signature>` token, then `/bookings`), `/business` landing for owners, `/business/new` registration, `/manage` my businesses, `/master` → `/master/<slug>` a master's own day, `/manage/<slug>` owner cabinet (`?tab=schedule|clients|analytics|reviews` on top; «Настройки» is `?tab=settings` — sections grouped like macOS System Settings (Бизнес: profile, branches, hours, notifications · Услуги и команда: services, masters, team · Продажи: promotions, loyalty, stock; `SETTINGS_GROUPS`, `SettingsNav`): a sidebar with coloured glyph tiles beside the open section from 1024px (the root opens «Услуги»), on phones the iOS Settings list alone and each section under a nav row «‹ Назад» with its title centred), `/ui` kit demo. Old `/book`, `/services`, `/admin`, `/profile` redirect to Awaisa Studio / `/manage`.
- A first path segment that isn't an app route is a business slug: keep `APP_SEGMENTS` (`shared/config/navigation.ts`) and `RESERVED_SLUGS` (`apps/api/src/businesses/business-rules.ts`) in sync when adding a top-level route.
- Architecture: Feature-Sliced Design. Layers, each importing only from layers below: `src/app/` (Next routes, layouts — thin files, default exports only here) → `src/views/` (one slice per page: `catalog`, `business`, `services`, `booking`, `bookings` (profile + records), `auth`, `forBusiness`, `manage`, `map`, `review`, `masterDay`; FSD «pages», renamed because Next reserves `pages/`) → `src/widgets/` (`Header`, `HeaderSearch`, `BusinessBar`, `Footer`, `TabBar`, `DayCalendar`, `DayStrip`) → `src/features/` (`theme`, `language`, `favorites`, `addToWallet`, `ticketView`, `bookingAlerts`, `bookingDraft`, `rateVisit`, `rescheduleBooking`, `waitlist`) → `src/entities/` (`business`, `booking`, `offer`, `session`) → `src/shared/` (`api`, `ui`, `lib`, `config`, `styles`). Every slice of views/widgets/features/entities has an `index.ts` public API that exports only what other layers use; import slices through it (`@/entities/booking`), never deep. Entities take features through slots (e.g. `OfferCard action`), not imports. Modules with React hooks carry `'use client'` so barrels stay safe for server components.
- Rendering: pages without data are static (SSG: `/business`, `/login`, `/ui`); every other route is Partial Prerendering — a static shell plus server-streamed data. `'use client'` views are still server-rendered to HTML; what matters is where data is read. Public data is server-rendered from the Cache Components cache (`shared/api/serverApi.ts`: `'use cache'` + `cacheLife('minutes'|'hours')` + `cacheTag('businesses' | 'business:<slug>')`); dynamic parts (search params, slugs) stream into the prerendered shell (Partial Prerendering). After an owner saves in the cabinet, `refreshBusiness(slug)` (server action, `shared/api/revalidate.ts`) calls `updateTag`, so the public page is fresh at once. Personal pages read the session on the server too (`shared/api/sessionApi.ts`, server-only: forwards the request's cookies to the API, `no-store`, always behind `<Suspense>`): `requireCustomer(next)` redirects guests to `/login?next=` before anything renders, `getSessionCustomer()` returns null for guests. `/bookings`, `/manage` (one business → straight to its cabinet), `/manage/<slug>`, `/master` (one place → its day), `/master/<slug>` and `/business/new` pass that customer to `SessionProvider` (`entities/session`, seeds `useSession` so there is no `/api/me` round trip) and the first data as `initial*` props; the client hooks skip their first fetch and refetch after edits. `/review/<id>` is rendered on the server from the SMS signature (`getVisitReviewOnServer`); `/map`'s first list comes from the cache (`listMapPlaces(kind)`), «Рядом со мной» refetches on the client. Live bits stay on the client (next free slots, schedule polling, the places marquee).
- SEO (`shared/lib/seo`): `app/sitemap.ts` (static pages + every business and its services), `app/robots.ts` (personal, booking, payment and API paths closed; `/manage`, `/master`, `/bookings`, `/login` as exact-path rules so slugs like `/masterclass` stay open), JSON-LD on the business page (`businessJsonLd`: schema.org type by kind, address, geo, hours, aggregateRating, offer catalog in KGS), `businessMetadata` (title, description, canonical, OG; noindex when unpublished) and generated share images (`app/opengraph-image.tsx`, `app/[slug]/opengraph-image.tsx` — the cover wins when there is one; `ogTint.ts` mirrors `pickTint` because images cannot read CSS variables). Absolute URLs come from `NEXT_PUBLIC_SITE_URL` (default https://awaisa.kg), set as `metadataBase` in the root layout.
- Data: server pages read `getBusiness(slug)` (business + branches + catalog, `notFound()` on 404), `listBusinesses(kind, q)`, `listOffers(kind, q)` and `listPopularServices(kind)`. Dynamic routes pass the `params` promise into `<Suspense>` so the shell stays prerendered. Business data reaches components as props. URL-aware chrome sits in `<Suspense>` in the root layout. Browser calls go through `shared/api/clientApi.ts` to `/api/*`, which `next.config.ts` rewrites to `API_URL` (same origin: no CORS, works in the mobile WebView).
- Coming from outside (2ГИС, Instagram, QR): the cabinet «Филиалы» lists «Ссылки для записи» — one `/<slug>/book?branch=<id>` per branch with «Копировать», so the client lands with their branch chosen. Guests' name and phone are kept after a booking (`entities/booking/lib/contactStorage.ts`, `awaisa:contact:v1`) and filled in next time.
- Client bookings: guests can book without an account; `localStorage` keeps `{ id, token, snapshot }` per booking (`entities/booking/lib/bookingStorage.ts`) and the token lets them view/cancel. Signed-in clients also get the server list (`GET /me/bookings`: their bookings plus any made on their verified number), merged with device bookings on `/bookings`.
- Session on the client: `useSession()` (`entities/session`) (one shared store, fetches `/api/me` once; `status` is `loading | guest | signedIn`), `useRequireSession()` redirects guests to `/login?next=…`. The session is an httpOnly cookie set by the API through the `/api` rewrite — never read it from JS. Booking contacts skip the phone field when signed in. Phones are shown with `formatPhone()`.
- API shapes live in `packages/contracts` (`@awaisa/contracts`, TypeScript only): the web reads them through `shared/api/types.ts` (a re-export), and every API controller handler the web calls declares its answer with them (`Promise<Booking>`, `Promise<Offer[]>` …), so a field renamed, removed or made nullable in the API fails `pnpm typecheck` instead of a page. Adding or changing an endpoint: put the shape in contracts, type the handler, call it from `clientApi` with the same type; name small answers too (`CreatedId`, `CheckoutLink`) instead of writing `{ url: string }` at the call. The API imports contracts with `import type` only (`common/contracts-imports.spec.ts` fails otherwise — Node cannot load the package's .ts at run time). Answers built from raw SQL are typed where the rows are read (`as Offer[]`), which the compiler cannot check — keep the SELECT's aliases equal to the contract's fields.

## App shell and responsive rules

- From 1400px `--layout-container-width` grows from 1120 to 1280px (`shell.css`) and the catalog grids take a fifth column (the «Работы мастеров» shelf still after two full rows). Header action labels are 12px medium under 22px glyphs. In the dark theme picture cards (`data-card`) get a 1px white 9% outline in place of shadows (the focus ring still wins). Unearned achievements: grey emoji at 70%, the title in the label colour, progress in the medal's own colour.

- Public: `GET /businesses?kind&q&offset&limit` (published businesses with at least one active service), `GET /businesses/offers?kind&q&offset&limit&sort=popular|price&ids` (one card per service, ≤ 60 a page; `ids` — comma-separated service ids — for favourites), `GET /businesses/:slug` (business + catalog), `GET /businesses/slug-available?slug`, `GET /availability?serviceId&specialistId&date[&branchId]`, `GET /map?lat&lng&kind&q` (pinned branches of published businesses, haversine `distanceKm`, nearest first), `GET /next-free?slugs=` (first free time today/tomorrow per business, quickest service, any master), `POST /bookings`, `GET|DELETE /bookings/:id` with `x-booking-token`. `specialistId=any` picks the first free specialist. Service ids are global, so the service decides the business.
- Businesses (`src/businesses`): `businesses`, `business_members` (owner/staff), `working_hours` (weekday 0 = Monday; no row = day off); categories, services, specialists and bookings carry `business_id`. New rows created by owners get UUID ids; new masters have no rating until reviews exist.
- Analytics (`src/admin/analytics.service.ts`): raw SQL aggregates over `bookings` × `services` in business time (UTC+6): totals and the previous period, daily series, top services, masters with load (booked minutes / open minutes from `working_hours`), clients grouped by phone (new = no earlier confirmed visit), weekday × hour heatmap, upcoming visits.
- Roles: `business_members.role` is `owner` or `staff` (shown as «Администратор»). `BusinessAccessGuard` lets members in; `@OwnerOnly()` (handler or controller) refuses staff with 403 «Это может только владелец» — analytics, business setup (profile, hours, branches, categories, services, specialists and their hours, photos), promotions, mailings, stock, loyalty settings/plans/issuing certificates, Telegram link/unlink, the team. Staff keep the day: schedule, bookings, outcomes (incl. loyalty redemption), time off, leaves, clients, waitlist, reviews. Platform admins count as owners. `GET /manage/:slug` returns `role`. The team: `GET|POST /manage/:slug/members` (`phone`; creates the customer if new and texts `adminInviteMessage`), `DELETE /manage/:slug/members/:customerId` (staff only; never yourself).
- Owners: `POST /businesses` (signed in; creates the business, owner membership, default hours 10–20 daily, a «Услуги» category and any template `services`), `GET /me/businesses`, and everything under `/manage/:slug` behind `BusinessAccessGuard` (member of the business or a platform admin from `ADMIN_PHONES`): profile `GET|PATCH`, `PUT hours`, categories, services (`PUT` full object; a new service is given to every active master), specialists, `GET schedule?date`, `POST bookings` (staff books a client in: phone required, same slot rules and SMS), `POST|PUT|DELETE branches` (the last branch can't be deleted or closed), `PATCH bookings/:id` (move: date, time, master; time off and overlaps refused, SMS after the undo window), `POST bookings/:id/cancel`, `POST bookings/:id/restore`, `GET bookings/recent?since`, `POST|DELETE time-off`, photos: `POST|DELETE cover`, `POST|DELETE photos`, `POST|DELETE specialists/:id/photo` (multipart `file`, ≤ 10 MB).
- Branches (`branches` table, `src/businesses/branch.entity.ts`): bookings store `branch_id` (the master's branch, else the requested one, else the first); a booking's view uses the branch address and phone. `map` and `review` are reserved slugs.
- Work photos (`src/media/work-photos.service.ts`, table `work_photos`: url, service, master, booking, is_hidden, reports; `businesses.photos` moved there): `GET /feed?kind&business&start&lat&lng&offset` (public, 12 a page: visible photos of published businesses, `start` first, then nearest by 3 km rings when a point is given, newest first), `POST /feed/:id/report` (3 reports hide a photo until the owner shows it again), `POST /manage/:slug/photos` (multipart `file` + optional `serviceId`, `specialistId`; ≤ 30), `GET|PATCH|DELETE /manage/:slug/work-photos[/:id]` (owner), `POST /master/:slug/photos` (`MasterGuard`, `bookingId` of their own visit). The business view's `photos` are the visible URLs, newest first. `feed` is a reserved slug.
- Photos (`src/media`): every upload is re-encoded by sharp (EXIF dropped, rotated, capped: cover 1600×1000, photo 1400 wide, avatar 480², WebP q80). `StorageService` writes to S3-compatible storage (Cloudflare R2) when `STORAGE_DRIVER=s3` / `S3_BUCKET` is set, else to `UPLOAD_DIR` served by `GET /media/:folder/:file` (`/api/media/…` from the web).
- Master accounts (`src/master`, `specialists.phone` E.164, set through `PUT /manage/:slug/specialists/:id` `phone`, returned only in the cabinet catalog): `GET /me/master` (places), `GET /master/:slug/day?date` and `PATCH /master/:slug/bookings/:id/outcome` behind `MasterGuard` (signed-in phone = an active master of the business; only their own bookings, others are 403). `master` is a reserved slug.
- Master schedules (`catalog/master-schedule.service.ts`, tables `specialist_hours` (no row = day off) and `specialist_leaves`, `specialists.has_own_hours`): `GET /manage/:slug/specialists/:id/schedule`, `PUT …/hours` (`hasOwnHours`, `days`), `POST|DELETE …/leaves`. A master's off hours and leaves become busy intervals (`master-hours.ts` `offHoursAsBusy`, unit-tested) inside the business window, so `buildSlots`, staff bookings, «любой мастер» and next-free respect them; moving a booking outside them is refused; `GET schedule` gives each master `hours` (null = off), `isOnLeave`, `leaveReason`.
- Signed visit links (`common/visit-link.ts`, unit-tested): `visitLink` = `/v/<id>?s=<HMAC('visit:'+id, AUTH_SECRET)>`, sent in the confirmation («Перенести или отменить»), reminder and reschedule SMS; any `x-booking-token` of the form `sig.<signature>` is accepted wherever the booking token is (view, cancel, restore, move).
- Client moves: `PATCH /bookings/:id` (`date`, `time`; device token or the signed-in owner) keeps the master and service, uses the same slot rules (the booking does not block its own new time), refuses visits that have started, resets the reminder, texts the client (if SMS is on) and tells the owner's Telegram «Клиент перенёс запись». Staff moves into the past are refused. `GET /manage/:slug/bookings/unclosed` lists ended visits without an outcome in the last 30 days per day. `specialists.commission_percent` (0–100) gives analytics masters `percent` and `payout`.
- Visit outcomes: `PATCH /manage/:slug/bookings/:id/outcome` (`outcome` arrived | no_show | null, `paidAmount`, `paymentMethod` cash | card | transfer; only confirmed bookings from their day on) → `bookings.outcome`, `paid_amount`, `payment_method`, `outcome_at`; admin views carry them. Analytics counts a visit unless it was a no-show and earns `COALESCE(paid_amount, price)`; totals add `noShows`, `noShowRate` and `payments` (cash, card, transfer, unmarked).
- Prepayment (`bookings/payments.service.ts`, `payments.controller.ts`, table `payments`; `services.deposit`, `bookings.deposit_amount | payment_status | payment_due_at | cancelled_by`): an online booking of a service with a deposit is created `confirmed` but `payment_status = pending`, holding its slot `PAYMENT_HOLD_MINUTES` (15) while the client pays; its confirmation SMS, reminder and the owner's Telegram wait for the payment. `POST /bookings` then returns `checkoutUrl`. `PAYMENT_DRIVER`: `test` (default outside production) is the built-in checkout — our `/pay/<id>?s=<HMAC('pay:'+id)>` page and `POST /payments/:id/test-complete?s=`; `none` (default in production) turns deposits off; `freedompay` takes cards through Freedom Pay (`bookings/freedompay.ts`, unit-tested signing: md5 of «script; values sorted by key; secret»): `init_payment.php` (order = our payment id, lifetime = the hold, result URL `<PUBLIC_WEB_URL>/api/payments/freedompay/result`, success/failure back to our `/pay`) → the client pays on their page → the result notification (signature checked with script `result`, answered with signed XML) and the client's return to `/pay` (`POST /payments/:id/sync?s=`) both confirm the status with `get_status3.php` before anything is marked paid; refunds go through `revoke.php`. Env: `FREEDOMPAY_MERCHANT_ID`, `FREEDOMPAY_SECRET_KEY`, `FREEDOMPAY_API_URL` (https://api.freedompay.kg), `FREEDOMPAY_CURRENCY` (KGS), `FREEDOMPAY_TESTING_MODE`. The acquirer being down at booking time cancels the hold at once (503 «Оплата сейчас недоступна»). `BookingPaymentsService.onPaid` confirms (paid after the hold ran out → refunded). `settlePayments` (every minute) releases unpaid holds (`expired`, booking cancelled, slot free) and, after the undo window, settles deposits of cancelled visits: refunded when the salon cancelled or the client cancelled ≥ `DEPOSIT_REFUND_HOURS` (24) ahead, else `kept`. `GET /payments/config`, `GET /payments/:id?s=`, `GET /bookings/:id/checkout` (token or session). Staff bookings never ask for a deposit. `pay` is a reserved slug.
- Waitlist (`src/waitlist`, table `waitlist_entries`: service, master or null = any, branch, day, name, phone, hashed token, status waiting | notified | cancelled | expired): `POST /waitlist` (OptionalAuth, booking rate limit; refused with 409 when the day has free time; one entry per phone, service, master and day), `GET|DELETE /waitlist/:id` with `x-waitlist-token`, `GET /me/waitlist`, `DELETE /me/waitlist/:id`; the cabinet reads `GET /manage/:slug/waitlist` (upcoming waiting/notified entries with name and phone; anyone who has since booked that day drops off) and `DELETE /manage/:slug/waitlist/:id`. `WaitlistService.notifyFreed` (every minute) expires past days and checks availability per (service, master, branch, day); when a time is free it claims the group (`UPDATE … WHERE status = 'waiting'`) and texts each client one `waitlistFreedMessage` with `/<slug>/book?service=&specialist=&date=&time=`. A cancellation still in its undo window is not counted.
- Promotions (`src/promotions`, table `promotions`: happy_hours (weekdays 0 = Monday, from/to minutes) | first_visit (no earlier confirmed visit on this phone at this business) | promo_code (unique per business, upper-case); percent 1–90, optional services and dates, on/off). Discounts never stack: `bestDiscount` (pure, unit-tested) picks the biggest. `POST /bookings` takes `promoCode` (an unknown code → 400 «Такого промокода нет») and stores `bookings.promotion_id | discount_amount | discount_title`; views carry `discount { title, amount }`, the client pays `price − discount.amount`, and that is what analytics, client spend, «Все пришли» and «Пришёл» use. `GET /promotions/quote?serviceId&date&time[&code][&phone]` (the session's phone when signed in), `GET /businesses/:slug/promotions` (open ones, no codes), `GET|POST|PUT|DELETE /manage/:slug/promotions`. Offers carry `discountPercent` (biggest open non-code promotion on that service). A deposit never exceeds the discounted price.
- Loyalty (`src/loyalty`, raw SQL in `LoyaltyService`): bonuses (`businesses.bonus_percent` 1–30; ledger `bonus_transactions` earn/spend/manual, unique per visit and kind), gift certificates (`gift_certificates`: 8-char code without look-alike letters, amount, balance, optional phone and expiry; `certificate_uses`), subscriptions (`subscription_plans`: title, service or any, visits, price, validity; sold into `client_subscriptions` with `visits_left`; `subscription_uses` one per visit). - Stock (`src/inventory`, raw SQL in `InventoryService`; tables `stock_items` (unit, quantity, unit_cost, min_quantity), `service_materials` (service, item, amount per visit), `stock_movements` (receive | use | adjust, cost; one `use` per visit and item)): `GET|POST /manage/:slug/stock`, `PUT|DELETE …/stock/:id` (the body carries `materials`), `POST …/stock/:id/receive` (`quantity`, optional new `unitCost`), `POST …/stock/:id/adjust` (counted `quantity`) — owner only. - Mailings (`src/mailings`, table `mailings`; `businesses.birthday_greeting`, `birthday_greetings` (business, phone, year)): SMS to a segment of the client base — `lapsed` (last visit older than N days, nothing booked), `birthday` (within the coming week, from client cards), `all` — only clients whose latest booking kept SMS on. Daily at 11:00 business time (`0 5 * * *` UTC) clients with a birthday today get the greeting once a year.
- Return visits («Пора прийти снова», `notifications/return-visits.service.ts`): a service may set `rebook_days` (cabinet service sheet: 2/3/4/6/8 weeks or 3 months). - Recommendations (`src/recommendations`), built like the big feeds — candidates from every active service, a transparent score, signals from behaviour, variety and exploration: `GET /recommendations?interests&gender&budget&lat&lng&visits=serviceId~YYYY-MM-DD,…&like&recent&session&limit` (`like`: the service being chosen — same kind +4, other kinds −3, same-person services +2, its gender read from its name when none is stated, past places and kinds ignored) (OptionalAuth: a signed-in client's past visits by phone are added). - Processes (`src/runtime`): one build, three ways to run. `PROCESS_ROLE` (process environment, validated in `env.ts`): `all` (default, `pnpm dev`) serves HTTP, runs the cron jobs and migrates on start; `api` (`node dist/main.js`) serves HTTP only and can be scaled; `worker` (`node dist/worker.js`, no HTTP, exactly one) runs every `@Cron`, the start-up affinity backfill and the Telegram long-poll / `setWebhook` (`RuntimeService.runsJobs`). `AppModule.forRole(role)` imports `ScheduleModule` only where jobs run, so an `api` process never fires a cron. Split roles refuse to start without `REDIS_URL`: the worker bumps cache tags the api instances must see, and rate limits count across instances. Migrations then run once per deploy with `pnpm --filter api migrate` (`dist/database/migrate.js`); compose has `migrate` → `api` + `worker`, sharing one image and the `x-api-env` block (add new env vars there).
- Monitoring: every server error (`ServerErrorsFilter`), browser error (`reportError` → `POST /telemetry/errors`), Next server-render error (`src/instrumentation.ts` `onRequestError`, posted to the same endpoint as `SSR <route>: …`) and failed cron job (`AppLogger` sees context `Scheduler` → `runtime/job-failures.ts` → `AlertsService` records `Cron: …`) lands in `app_errors` through `TelemetryService.recordError`, which also sends it to Sentry when `SENTRY_DSN` is set (`runtime/sentry.ts`, `@sentry/node` on the server only — the browser carries no SDK; no tracing or auto-instrumentation; `dataCollection` off; `runtime/error-scrub.ts` replaces phones and long numbers and drops query strings; grouped by source + message with ids folded; works with GlitchTip too). `AlertsService` (jobs process, every 5 min) texts `ALERT_TELEGRAM_CHAT_ID` through the owners' bot (`/chatid` tells a chat its id): any new server error, browser errors only in a burst (≥ 10 in a check), Redis not answering; the same alert repeats at most hourly. `.github/workflows/uptime.yml` checks `vars.UPTIME_URLS` from outside every 5 minutes (three tries) and texts the same chat via `secrets.ALERT_TELEGRAM_BOT_TOKEN` / `ALERT_TELEGRAM_CHAT_ID`; it is skipped until the variable is set. `/health` adds `cache: redis | memory` and is 503 only when the database is down. Settings read before Nest starts (`PROCESS_ROLE`, `SENTRY_*`) come from the root `.env` via `loadRootEnv`.
- Rate limits (`cache/rate-limit.storage.ts`, `RateLimitStorage`, the `ThrottlerModule` storage): one fixed-window counter per key in Redis (`rl:<throttler>:<key>`, a Lua `INCR` + `PEXPIRE`, a `:block` key past the limit), so a limit holds across every api instance and a deploy; no Redis or a Redis error falls back to in-process counters, never a failed request. The cache's Redis connection is opened even with `API_CACHE=off` for this.
- Database (`database.module.ts`): `DATABASE_POOL_SIZE` (10) connections per process, `DATABASE_STATEMENT_TIMEOUT_MS` (30 s; the compose worker gets 300 s) cancels runaway queries, idle transactions end after 60 s, a full pool errors after 5 s, `application_name` is `awaisa-<role>`. Queries over 1 s are logged as warnings by `DatabaseLogger` (SQL only, never parameters). Foreign keys are indexed (`ForeignKeyIndexes` migration) — index a new foreign key in the migration that adds it. `pg_stat_statements` is preloaded by compose's Postgres and enabled by the optional `QueryStats` migration; `pnpm --filter api db:slow` lists the 15 queries with the most total time (`-- --reset` clears the statistics). Measured on demo data (16k bookings), uncached: public endpoints under 10 ms, `/recommendations` ~20 ms.
- Free times in bulk (`AvailabilityService.firstFreeTimes`, behind `findNextFree`, `findNextFreeByService` and «Для вас»): the same answer as `getAvailability` day by day, but loaded in about nine queries however many places or services are asked (services, businesses, masters per service, opening windows, bookings and time off over both days, `MasterScheduleService.offHoursBusyMany`), then `buildSlots` in memory — it was ~8 queries per place per day (519 → 9 for the whole catalog). Keep it that way: never call `getAvailability` in a loop; add a batch loader next to the single one (`getActiveServices`, `getSpecialistsForServices`, `findByIds`, `getOpeningWindows`).
- Logs: `createLogger()` — Nest `ConsoleLogger`, one JSON object per line in production. `requestLog` writes `METHOD /path status ms id=…` per request (no query string: it may carry phones), errors for 5xx, `slow` from 1 s, and returns `x-request-id`. HTTP keep-alive is 65 s so a load balancer never reuses a closed connection.

## Accounts, SMS and admin (apps/api)

- Sign-in by phone: `POST /auth/otp` (`channel: auto | sms`) → 6-digit code, sent to Telegram through the Telegram Gateway when `TELEGRAM_GATEWAY_TOKEN` is set (`checkSendAbility` pays, the send with its `request_id` is free, `ttl` refunds undelivered codes) and by SMS otherwise or when Telegram refuses the number; the response says which `channel` was used and the login page offers "Нет Telegram? Получить SMS". The resend cooldown is per channel. The code itself is ours (HMAC-hashed with `AUTH_SECRET`, 5 min, 5 attempts, one per 60 s and 10 per day per number), `POST /auth/verify` → creates the customer if new and sets the `awaisa_session` cookie (opaque token, sha256 in `sessions`, 30 days), `POST /auth/logout`. Phones are normalized to E.164 by `common/phone.ts` (`0555…`/`555…` → `+996555…`). Texts and login codes go only to `SMS_ALLOWED_COUNTRY_CODES` (default `996`; `SmsService.canSendTo`, `isAllowedDestination`): `POST /auth/otp` refuses other numbers with 400 before anything is sent (Telegram codes cost money too), and booking, reminder and waitlist SMS to them are skipped — bookings still go through. A code attempt is taken atomically (`UPDATE … attempts + 1 WHERE attempts < 5 RETURNING`) before the comparison, so parallel guesses get five tries in all.
- Sign-in through the Telegram bot («Войти через Telegram», `auth/telegram-login.service.ts`, table `telegram_logins`; pure `auth/telegram-login.ts`, unit-tested): the page makes a random 43-char token, registers it with `POST /auth/telegram` (`{ token }`, 204; `GET /auth/telegram` says `isAvailable` and the bot) and opens `t.me/<bot>?start=login_<token>`; the bot ties the chat to the token and asks «Поделиться номером» (a `request_contact` keyboard); only the person's own contact counts (`contact.user_id === from.id`, a forwarded one is refused), numbers outside `SMS_ALLOWED_COUNTRY_CODES` too; it confirms the chat's latest open token (10 minutes) and links that number's client messages to the chat. The page polls `POST /auth/telegram/check` (`pending | expired | signedIn` + customer); a confirmed token opens a session once (`AuthService.openSession`, shared with SMS sign-in) — the same account as by SMS on that number.
- Guards: `AuthGuard`, `OptionalAuthGuard` (booking creation links the booking to the signed-in customer and uses their verified phone), `AdminGuard` (`ADMIN_PHONES`). `@CurrentCustomer()` reads the customer.
- Profile: `POST|DELETE /me/avatar` (`src/media/me-avatar.controller.ts`, multipart `file` → 480² WebP under `customers/`, `customers.avatar_url`, returned as `avatarUrl` in the customer view), `GET|PATCH /me` (`GET` adds `businesses` — slug, name, role of each membership — and `masterOf` — places where the number is an active master — for the profile's cabinet shortcut, the tab bar and the header), `GET /me/bookings`, `DELETE /me/bookings/:id`.
- Schedule (`/manage/:slug/…`): masters, bookings with phones and comments, time off; cancelling texts the client. Time off is subtracted from availability like a booking; the response lists bookings that fall inside it. `ADMIN_PHONES` are platform admins with access to every business.
- SMS: `SmsService` sends through Twilio's REST API when `SMS_DRIVER=twilio` (or Twilio credentials are present), otherwise logs messages (`SMS to …`) — read codes from the API log in development. Texts live in `notifications/messages.ts` (Cyrillic SMS segments are 70/67 characters). Confirmation goes out on booking unless the client turned it off (`sms_confirmation`), a reminder `reminder_minutes` (60 / 120 / 1440, null = none, default 120) before the visit («сегодня/завтра» in the text) from a 5-minute cron (`RemindersService`, rows claimed with `UPDATE … RETURNING`, safe with several instances), and a notice when the salon cancels. Booking flows never fail because of SMS (`sendSafely`).
- Env (photos, wallet): `STORAGE_DRIVER`, `UPLOAD_DIR`, `S3_BUCKET`, `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_PUBLIC_URL`; `WALLET_PASS_TYPE_ID`, `WALLET_TEAM_ID`, `WALLET_CERT_PEM`, `WALLET_KEY_PEM`, `WALLET_KEY_PASSPHRASE`, `WALLET_WWDR_PEM`, `GOOGLE_WALLET_ISSUER_ID`, `GOOGLE_WALLET_SERVICE_ACCOUNT` (PEM/JSON raw or base64).
- Env: `AUTH_SECRET` (required in production, ≥ 32 chars), `ADMIN_PHONES`, `PUBLIC_WEB_URL` (links in SMS), `SMS_DRIVER`, `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM` or `TWILIO_MESSAGING_SERVICE_SID`, `TELEGRAM_GATEWAY_TOKEN`, `AUTH_RATE_LIMIT_PER_MINUTE`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` (turns the cabinet section on), `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_WEBHOOK_URL`. `OTP_TEST_CODE` fixes the code and drops the per-number limits for tests; it is rejected in production.

## Code style

Follows https://react-typescript-style-guide.com/, enforced by Biome where possible:

- Single quotes (JS and JSX), no semicolons, trailing commas.
- Components are arrow functions with named exports: `export const ProfileHero = () => {}`. Default exports only where a framework requires them (Next.js `page`/`layout`, `*.config.ts`).
- `interface` for component props, `type` for everything else.
- Component order: hooks → variables → `useEffect` → handlers → `return`. Early returns over `else`.
- Folders follow FSD segments: `ui/<Name>/<Name>.tsx`, `model/useX.ts`, `lib/`, `api/`, `config/` inside a slice; `shared/{ui,lib,lib/hooks,api,config,styles}`.
- Files: components PascalCase, everything else camelCase. The API keeps Nest naming (`*.module.ts`, `*.controller.ts`).
- Several exports from one file go in a single `export { ... }` at the bottom.
- No comments that restate code; comment only the "why" (workarounds, platform quirks).

## Conventions

- Lint/format: Biome only (root `biome.json`, per-app overrides in `apps/*/biome.json`). No ESLint/Prettier.
- API: Biome `useImportType` is off — Nest DI needs runtime imports for constructor-injected classes.

Past visits come from `e2e/visits.ts` (a real booking moved back in the database).
- `reviews.spec.ts` — a visit moved into the past is rated from the signed SMS link (no stars → inline hint, one review per visit), shows on the business page, the owner replies; a wrong signature opens nothing; the owner links a Telegram chat via a simulated `/start` webhook and unlinks it. It restores the master's rating afterwards.
- `catalog.spec.ts` — the services feed loads the next page near its end; pages continue one price order without repeats; a place shows «Похожие места» of its kind without itself; hearted services show in the profile under «Избранное» and the heart takes one off.
- `recommendations.spec.ts` — the catalog grid carries «Для вас» for a new guest; a guest answers the three questions in the profile and «Для вас» shows nail services with their reason and no men's services; a visit five weeks ago puts that service first with «Пора снова»; at most two per place; unknown interests are 400. The catalog shelf records impressions and a tap for the device session (read back from the database); `like=` a manicure puts nails first with no men's services and itself left out; an empty event batch is 400.
- `feed.spec.ts` — the owner adds a work photo in the cabinet and tags service and master in the sheet; a guest opens `/feed?start=` and «Записаться» opens booking with that service and master; three reports hide it; the kind chips mark the chosen kind.
- `reviewers.spec.ts` — a review's `authorId` opens that person's reviews and profile (no phone in it, made-up ids 404), `serviceId` filters a place's reviews, and the author's name on the business page leads to `/u/<id>`.
- `profile.spec.ts` — a handle (reserved → 409, malformed → 400) opens `/u/<handle>` with «Пригласить» and «В сторис»; a friend's past visit booked with that `ref` counts as a friend and earns «Привёл друга»; the story card is a PNG. A client sets colour and status through `/me/profile`, the public page shows them with level, achievements («0 из 10») and «Поделиться»; an unknown banner is 400; a hidden profile is 404 to others and noted for the owner; the settings sheet opens with the saved look and turns the profile back on.
- `leaderboard.spec.ts` — the barbers' board is ordered with ≥ 3 reviews each, an unknown kind is 400, the podium's first books that master, the «Ногти» tab switches the board.
- `growth.spec.ts` — a signed-in client books mum («Записать другого человека», her number) and the booking stays in the account; the Telegram link endpoint answers; the form speaks Kyrgyz from `awaisa:lang:v1`; funnel steps and web errors are stored, 400 for unknown steps, readable only by platform admins.
- `seo.spec.ts` — sitemap lists businesses, robots closes the cabinet, the business page has JSON-LD, OG tags and a canonical, share images render as PNG.
- `a11y.spec.ts` — no serious/critical axe violations (WCAG 2.1 AA) on every page.
- Gestures on sheets measure their target with `settledBox` (`e2e/helpers.ts`) — a box taken while a sheet still slides makes the drag miss on slow runners; `/map` tests open it with `openMap`, which waits for a visible place row (the streamed page sits over a pending copy of itself until React swaps them). A test that changes shared data restores it to the seed when what it found is its own leftover (`prepayment.spec.ts`).
- Test data (bookings, businesses, customers) is named `E2E …` and deleted by `e2e/globalTeardown.ts` after the run (uses `DATABASE_URL` from the root `.env`).
