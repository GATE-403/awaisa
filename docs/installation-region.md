# Регион установки: Awaisa для любой страны

Сейчас Awaisa сделана для Кыргызстана: часовой пояс, номер телефона, валюта, город, фискальные чеки и тексты зашиты в код. Цель документа: план, как сделать так, чтобы любой бизнес мог поставить систему у себя и настроить её под свою страну, не форкая код.

Главное решение: **один регион на установку**. Салон в Алматы ставит свой экземпляр с казахстанскими настройками, салон в Бишкеке пользуется awaisa.kg. Несколько стран в одной базе (разные пояса и валюты у разных бизнесов) в разы дороже и для «поставить себе» не нужно; это отдельный этап в самом конце, если вообще понадобится.

Запуск в январе 2027 идёт с кыргызскими значениями. Всё, что ниже, для Кыргызстана поведение не меняет: регион по умолчанию равен сегодняшнему.

## 1. Что уже готово

Провайдеры уже выбираются окружением, это правильный фундамент (`apps/api/src/config/env.ts`):

| Что | Переменная | Сейчас умеет |
| --- | --- | --- |
| SMS | `SMS_DRIVER` | `twilio` (работает в любой стране), `console` |
| Коды входа | `TELEGRAM_GATEWAY_TOKEN` | Telegram Gateway (международный) |
| Оплата | `PAYMENT_DRIVER` | `freedompay` (Кыргызстан), `test`, `none` |
| Чеки | `FISCAL_DRIVER` | `ekassa` (Кыргызстан), `log`, `off` |
| Хранилище | `STORAGE_DRIVER` | любой S3-совместимый |
| Геокодер | `GEOCODER` | Photon (OpenStreetMap, весь мир) |
| WhatsApp | `WHATSAPP_DRIVER` | Meta Cloud API (весь мир) |
| Куда слать SMS | `SMS_ALLOWED_COUNTRY_CODES` | любые коды стран |

Telegram, WhatsApp, Twilio, Photon и OpenStreetMap международные: их обобщать не нужно. Кыргызские только Freedom Pay и eKassa, и они уже отделены драйвером.

## 3. Как устроить регион

Один пакет `packages/region` (как `packages/tokens`): обычный TypeScript, который читают и API, и веб, и мобильное приложение.

```ts
// packages/region/src/kg.ts
export const KG: Region = {
  key: 'kg',
  country: 'KG',
  timeZone: 'Asia/Bishkek',
  phone: { countryCode: '996', localDigits: 9, trunkPrefix: '0', mask: '### ### ###' },
  currency: { code: 'KGS', symbol: 'сом', minorUnits: 0 },
  locale: { default: 'ru', available: ['ru', 'ky', 'en'] },
  city: { name: 'Бишкек', center: { latitude: 42.8746, longitude: 74.5698 }, areas: [/* районы */] },
  geocoderBox: [69.2, 39.1, 80.3, 43.3],
  fiscal: 'kg-ekassa',
  payments: ['freedompay'],
}
```

- Выбор региона: `REGION=kg` в окружении API и `NEXT_PUBLIC_REGION=kg` в аргументах сборки веба (как `NEXT_PUBLIC_SITE_URL` в `docs/launch.md`). Без переменной `kg`, то есть ровно сегодняшнее поведение.
- Новая страна: файл `packages/region/src/kz.ts` в PR, без правок остального кода. Это и есть «кастомизация без форка».
- Мелкие правки без нового пресета (другой город той же страны): переменные `REGION_CITY`, `REGION_CENTER` поверх пресета.
- `GET /region` в API не нужен: и веб, и API читают один и тот же пакет при старте или сборке.

## 4. План по шагам

Оценки для одного разработчика с Claude, в днях работы. Каждый шаг отдельным PR, после каждого CI и e2e зелёные, для Кыргызстана видимых изменений нет.

### Шаг 1. Пакет региона и простые константы (2-3 дня), можно в декабре

- `packages/region` с пресетом `kg` и юнит-тестами.
- Заменить константами из пресета: код страны и разбор номера (`phone.ts`, `inputMasks.ts`, `formatPhone.ts`), валюту (`formatPrice` через `Intl.NumberFormat` с кодом валюты и коротким названием из пресета), центр карты, районы, рамку Photon, `PLATFORM.name` и `tagline`, `Asia/Bishkek` в `ics.ts` и `businessTime.ts`.
- Проверка: юнит-тесты `normalizePhone` и масок на кыргызских номерах дают то же, e2e целиком.
- Риск низкий: значения те же, меняется только откуда они берутся.

### Шаг 2. Время по часовому поясу, а не по смещению (3-5 дней), лучше в декабре, пока нет реальных денег

- SQL: 15 мест `AT TIME ZONE 'UTC' + interval '6 hours'` заменить на `AT TIME ZONE $tz` с поясом из региона (Postgres сам знает летнее время). Сначала одно выражение-хелпер (`localDate(column)`), потом подстановка. Это пересекается с пунктом 8 из `docs/architecture-review.md` (SQL-хелперы денег и визитов): делать вместе.
- `business-time.ts`: перевод «день и минуты бизнеса ↔ UTC» через `Intl.DateTimeFormat` с `timeZone`, без фиксированного смещения. Свободное время (`buildSlots`) от этого зависит напрямую, юнит-тесты уже есть.
- Cron: `@Cron('0 10 * * *', { timeZone: REGION.timeZone })` с локальными часами вместо пересчитанных в UTC (9 задач).
- Проверка: отчёты «Аналитика», «Прибыль», зарплата и `test:db` на демо-данных до и после: суммы совпадают до сома. Плюс новые юнит-тесты на пояс с переходом на летнее время (`Europe/Moscow` без перехода, `Europe/Berlin` с ним): запись через ночь перехода, слоты дня перехода.
- Риск средний: трогает деньги. Именно поэтому до запуска, когда ошибку ловит сравнение на демо-данных, а не жалоба владельца салона.

### Шаг 3. Тексты сервера на языке региона (4-5 дней), после запуска

- SMS, Telegram, WhatsApp, пуши: тот же подход, что `shared/i18n` в вебе (русский текст как ключ, переводы рядом). Язык по умолчанию из региона.
- Шаблоны WhatsApp регистрируются в Meta на каждом языке отдельно (`docs/whatsapp.md`).
- Подсчёт сегментов SMS: кириллица 70, латиница 160 символов; `mailing-text.ts` должен считать по алфавиту текста.

### Шаг 4. Страновые модули за интерфейсом (по 1-3 дня на провайдера), когда появится страна

- `FiscalDriver` и `PaymentDriver` описать как интерфейсы с документацией: что передаётся, что возвращается, как тестировать. Кыргызские реализации (eKassa, Freedom Pay) становятся примерами.
- Регион перечисляет, какие из них доступны; кабинет показывает «Касса → чеки» только если фискальный модуль региона есть.
- Второй платёжный провайдер, если нужен международный: Stripe. SMS-шлюз по HTTP с настраиваемым шаблоном запроса закроет большинство местных SMS-провайдеров.

### Шаг 5. Открытая установка (3-4 дня), после запуска

- **Лицензия.** Предлагаю AGPL-3.0: любой может поставить себе и менять код, но если запускает как сервис для других, обязан открыть свои правки. MIT позволил бы сделать из Awaisa закрытый конкурирующий SaaS.
- **Тарифы выключаются:** `BILLING=off`, и у всех бизнесов установки всё открыто, как сейчас у тарифа «Основатель». Тарифы нужны вам как SaaS, а не тому, кто ставит себе.
- **Бренд:** название, логотип, адрес сайта, цвета из настроек (цвета уже в `packages/tokens`). Маскот остаётся по умолчанию.
- **Документация для себя-хостинга:** `docs/launch.md` уже почти она; плюс «как добавить свою страну».
- **Нейтральные демо-данные:** сид с городом из региона, а не только Бишкек.

### Шаг 6. Деньги с копейками (5-8 дней), только если цель страна с центами

- Все денежные колонки из целых сом в минимальные единицы (`price` × 100), контракты и форматирование через `currency.minorUnits`. Это трогает схему, все отчёты, кассу, чеки, оплату.
- Для сомов, тенге, рублей, сумов не нужно: там на практике цены целые. Нужно для USD, EUR, TRY и т. п.

### Шаг 7. Несколько стран в одной базе: не делать

- Пояс и валюта у каждого бизнеса, а не у установки. Каждый SQL-отчёт и каждая сводка по нескольким бизнесам (`/manage`, `/insights`) начинает смешивать валюты и дни.
- Нужно только если вы сами захотите вести один SaaS на несколько стран. Для «любой бизнес ставит себе» хватает шагов 1-5.

## 5. Порядок с учётом январского запуска

| Когда | Что |
| --- | --- |
| Декабрь, первая половина | Шаг 1 и шаг 2 (вместе с пунктом 8 аудита) |
| Декабрь, вторая половина | Заморозка кода, пилот с салонами (`docs/launch.md`) |
| Январь | Запуск в Кыргызстане |
| Февраль и дальше | Шаг 5 (открыть код), шаг 3 (языки сервера), шаги 4 и 6 по мере появления стран |

## 6. Что не трогать ради этого до запуска

- Путь записи (`BookingPage`, `useBookingForm`, `BookingsService.create`): регион входит в него только через `formatPrice` и время, этого достаточно.
- Тексты SMS и WhatsApp: их переделка в шаге 3, после запуска (шаблоны WhatsApp сверяются с Meta слово в слово).
- Фискальный модуль: изолировать в шаге 4, сам расчёт налогов не менять.
