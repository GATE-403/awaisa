# Рекомендации «Для вас»: что улучшать дальше

Ноябрь 2026. Основа — офлайн-оценка [`offline-eval-2026-11-18.md`](offline-eval-2026-11-18.md)
(`pnpm rec:eval`) и разбор формулы `apps/api/src/recommendations/recommend-score.ts`.

> **Данные синтетические.** Демо-база (`pnpm db:seed`) выбирает услугу каждого визита случайно,
> а симуляция поведения устроена так, как мы предполагаем о людях. Цифры ниже показывают
> направление и порядок величины, а не то, что увидят настоящие клиенты. Решения о проде —
> после онлайн-проверки ([experiments.md](experiments.md)).

## Что показала оценка

| | Демо-база NDCG@10 / Hit@10 | Симуляция NDCG@10 / Hit@10 |
|---|---|---|
| popular | 0.046 / 10% | 0.109 / 26% |
| popular-in-category | 0.092 / 19% | 0.186 / 42% |
| **score-v1 (прод)** | **0.101 / 17%** | **0.209 / 33%** |
| proto-usual | 0.105 / 18% | **0.336 / 48%** |

1. **Формула лучше «самого популярного», но не лучше «популярного в вашей категории» по HitRate.**
   По NDCG она чуть впереди (порядок лучше), по доле клиентов с хотя бы одним попаданием — позади
   на 2–9 п. п. Формула раскладывает ленту по разным типам услуг (разнообразие 0.75–0.89 против
   0.49–0.75) и показывает почти весь каталог (85–97% против 36%). Это сознательный выбор, но
   цена в точности есть.
2. **Своя прошлая услуга клиента часто пропадает из ленты.** Правило «одно название — одна
   карточка» оставляет вариант с наибольшими очками. Если клиент ходит на «Стрижку + бороду» в одно
   место, а то же название в другом месте набрало больше, своя карточка исчезает. Плюс «рано»
   (−2) гасит услугу, до которой осталась неделя. Отсюда огромный отрыв проверочной модели
   `repeat-places` (0.234 / 0.586 NDCG): люди в основном записываются на то же, что брали.
3. **Слот «Новое место» стоит ~3% точности** (score-v1-no-explore чуть выше). Это ожидаемо: его
   польза (новые салоны вообще видны) офлайн не измеряется.
4. **«Часто берут» по типам почти не срабатывает:** в демо-данных у 11 из 12 пар lift ниже 1.3.
   Проверить на настоящих данных.
5. **Пол угадывается только по названию.** Галине (68, в анкете «женщина») формула показывает
   «Стрижку машинкой» и «Детскую стрижку» в барбершопах: в названии нет слова «мужская».

## Что делать, по ожидаемому эффекту

### 1. Своё обычное — первым (прототип `proto-usual`)

Свои прошлые услуги клиента — привычка, а не только «пора»: «пора» с запасом в неделю (люди
записываются заранее), +1 за каждый повтор (до +3), и правило «одно название» не должно
выбрасывать именно его место.

- Офлайн: симуляция NDCG 0.209 → **0.336** (+61%), Hit 33% → **48%**, у постоянных (3+ визита)
  NDCG 0.228 → 0.441. Демо-база: 0.101 → 0.105, в пределах ДИ: там визиты случайны, привычек нет.
- Цена: «Hit новое» 26.6% → 25.0% (на 1.6 п. п. реже попадаем в новое для клиента).
- **Решение за владельцем:** что такое «Для вас»? Если это и «записаться снова», делаем. Если
  повторы живут в «Снова к мастеру» (`features/rebook`, панель поиска), а «Для вас» — про новое,
  то главная метрика — «Hit новое», и этот пункт не нужен. Тогда стоит наоборот убрать «Пора снова»
  с полки.
- Работы: ~полдня в `recommend-score.ts` (новая версия `score-v2`) + юнит-тесты.

### 2. Пол и аудитория — ещё и по типу места

Барбершоп = мужская аудитория, если в названии услуги не сказано иное; «Детская стрижка» — только
для тех, кто искал детское. Ожидаемый эффект — меньше явных промахов, которые подрывают доверие
к полке. В метриках симуляции он мал (там пол уже учтён), лучше видно на персонах через
`pnpm rec:judge`. Работы: час.

### 3. Подключить `like=` на экране успеха и в записи

API уже умеет держать ленту рядом с выбранной услугой (`like=`: тот же тип +4, другие −3), но
веб его не отправляет: `ForYouShelf likeServiceId` нигде не передаётся, экран успеха шлёт только
`seedVisit`. Офлайн это не оценить: нет истории «что человек выбирал в моменте». Работы: строка
в `BookingSuccess`, затем проверка в эксперименте.

### 4. «После этой услуги берут ту» по услугам (прототип `proto-covisit`)

Lift пар названий за 60 дней вместо пар типов. Офлайн: демо-база 0.101 → 0.105, симуляция
0.209 → 0.206 — **нейтрально**, в пределах ДИ. Держать в запасе до настоящих данных: связи в
демо-данных случайны, а в симуляции заложены на уровне типов и уже ловятся.

### 5. Веса из логов вместо ручных

Когда логирование из этого PR накопит показы и записи (ориентир — 50 000 показов и несколько
сотен записей с полки), обучить веса частей формулы (логистическая регрессия по `request_id`,
потом LambdaMART), сохранив прозрачные причины. До этого данных нет.

### Проверено и отложено

- **Личный ритм вместо 28 дней (`proto-own-cycle`):** симуляция 0.209 → 0.215, демо 0.101 → 0.108,
  оба в пределах ДИ. Главную пользу даёт пункт 1; вернуться, когда будут настоящие ритмы.
- **Слот «Новое место»:** оставить. Его цена (~3%) — плата за то, что новые салоны вообще видны.
  Проверять онлайн по доле записей в новые места.
