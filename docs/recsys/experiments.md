# Онлайн-эксперименты с рекомендациями

Логирование, на которое всё опирается, уже есть: у каждого ответа `GET /recommendations` есть
`requestId` и `algorithm`, они приходят во все события `recommendation_events`, а `book` несёт
`booking_id`. **Interleaving (раздел 2) сделан и выключен; A/B (разделы 1, 3–5) — пока
предложение.**

## Как запустить interleaving `score-v2` против `score-v1`

1. В окружении API (в compose — блок `x-api-env`): `RECS_INTERLEAVE=score-v1:50`. Половина
   устройств по хешу (`interleave.ts`: `isInterleaved`) получает ленты, собранные
   team-draft из двух формул. Остальные видят одну `score-v2`.
2. Через две недели вызвать `GET /recommendations/interleaving?days=14` (вход админа платформы).
   В ответе: сколько смешанных лент показано, победы каждой формулы по нажатиям и по записям,
   ничьи и p-value знакового теста.
3. Если по нажатиям p < 0.05 в пользу одной формулы, она остаётся (или возвращается, если это
   `score-v1`). Если p ≥ 0.05, а трафика по `pnpm rec:traffic` хватило бы на 55/45, разницы нет:
   оставляем `score-v2`. Потом `RECS_INTERLEAVE` пустая.

Смешанная лента соблюдает те же правила полки (≤ 2 на место, одно название). Каждая формула
считает на две глубины лимита, чтобы у неё были запасные карточки.

## 1. Назначение варианта

- **Единица — устройство** (`awaisa:device:v1`, отправляется как `session`). Большинство клиентов
  гости, а одному человеку нужно видеть одну и ту же полку. Вошедшим клиентам с несколькими
  устройствами позже можно перейти на `customer_id`. Пока такое смешение принимаем и проверяем
  его долю.
- **Стабильный хеш:** `bucket = sha256(experimentId + ':' + session)` → первые 8 hex → число
  mod 10 000. Вариант выбирается по диапазонам (например, 0–4999 — `score-v1`, 5000–9999 —
  `score-v2`). Без таблицы назначений: тот же ответ на любом инстансе API и после деплоя. Новый
  `experimentId` перемешивает людей, поэтому эксперименты не наследуют друг друга.
- **Где решается:** в `RecommendationsService.recommend` по `query.session`. Вариант пишется в уже
  существующее поле `algorithm` (`score-v1`, `score-v2-usual`). Отдельный лог экспозиции не нужен:
  экспозиция — это `impression` с этим `algorithm`.
- **Выключатель:** переменная окружения `RECS_EXPERIMENT=off|<id>:<split>` в `env.ts`. Откат за
  минуту, без миграций.
- **SRM-проверка:** раз в день χ² по числу сессий в вариантах. Перекос больше p < 0.001 —
  остановить и искать ошибку (кэш, бот, падающий вариант).

## 2. Interleaving — первым

При нашем трафике A/B по записям будет идти месяцами (раздел 4). Interleaving сравнивает два
алгоритма внутри одной полки и в 10–100 раз чувствительнее.

- **Team-draft:** A и B по очереди (кто первый — монетка на каждый запрос) отдают свой лучший ещё
  не взятый вариант, пока не наберётся `limit`. Правила полки (≤ 2 на место, одно название, слот
  «Новое место») применяются к общему списку.
- **Учёт:** у каждой карточки в поле `algorithm` записан алгоритм, который её дал. Значит, нужен
  только новый режим в API, без изменений в схеме и на вебе.
- **Победитель в сессии:** у кого больше кликов (а отдельно — записей) по его карточкам. Итог —
  доля сессий, где выиграл B, среди сессий с кликом; знаковый тест против 50%.
- **Ограничение:** interleaving отвечает «какой порядок лучше», но не «выросли ли записи в целом».
  Победителя затем подтверждаем коротким A/B.

## 3. Метрики

| Роль | Метрика | Как считается |
|---|---|---|
| Главная (interleaving) | Доля выигранных сессий по кликам | team-draft, сессии с ≥ 1 кликом |
| Главная (A/B) | Записи с полки на сессию с показом | `book` с `booking_id` / сессии с `impression` |
| Вторичная | CTR полки | сессии с кликом / сессии с показом |
| Вторичная | Hit по новому | записи на услугу, которой у клиента раньше не было |
| Вторичная | Позиция клика | средний `position` у `click` |
| Защитная | Все записи в каталоге на сессию | `funnel_events` `booked` — полка не должна забирать записи у остальной страницы |
| Защитная | Отмены записей с полки | доля отменённых за 7 дней |
| Защитная | Записи в новые места (< 5 отзывов) | не должны упасть больше чем на 20% от контроля |
| Защитная | Покрытие каталога | доля услуг, показанных хоть раз за неделю |
| Защитная | p95 `GET /recommendations` | не больше +50 мс |

Окно засчитывания записи — та же вкладка (как сейчас в `trackBookedPick`). Записи «после
просмотра без клика» не засчитываем: без клика нет честной связи.

## 4. Сколько нужно трафика

Тест двух долей, α = 0.05 (двусторонний), мощность 80%:
`n на вариант ≈ 7.85 · (p₁(1−p₁) + p₂(1−p₂)) / (p₁ − p₂)²`.

Реального трафика пока нет. Поэтому базовые доли — допущения, которые надо заменить через две
недели логов: CTR полки 5% сессий, запись с полки 1% сессий.

| Что ловим | Нужно сессий с показом на вариант | 500 сессий/день | 2 000/день | 10 000/день |
|---|---|---|---|---|
| CTR 5% → 6% (+20%) | ≈ 8 200 | 33 дня | 8 дней | 2 дня |
| CTR 5% → 5.5% (+10%) | ≈ 31 200 | 125 дней | 31 день | 6 дней |
| Записи 1% → 1.2% (+20%) | ≈ 42 600 | 170 дней | 43 дня | 9 дней |
| Interleaving, 55% против 50% | ≈ 780 сессий с кликом | ≈ 31 день* | ≈ 8 дней* | 2 дня* |

\* при CTR 5%: 780 / 0.05 ≈ 15 600 сессий с показом на весь эксперимент (одна группа, не две).

Длительность в днях — для двух вариантов поровну, все сессии с показом участвуют. Независимо от
расчёта — **не меньше двух полных недель**: в салонах запись зависит от дня недели, а у новой полки
есть эффект новизны.

**Вывод для текущего трафика:** пока сессий с полкой меньше ~2 000 в день, A/B по записям не
дождаться. Порядок такой: офлайн (`pnpm rec:eval`) и персоны (`pnpm rec:judge`) → interleaving по
кликам → A/B по записям, когда трафик вырастет.

**Настоящие цифры вместо допущений:** `pnpm rec:traffic -- --days=14` считает сессии с показом,
нажатием и записью по дням и версиям из `recommendation_events` (только чтение) и пересчитывает
эту таблицу на них. Запускать на копии или реплике прода (`DATABASE_URL`). Локальная база
содержит только следы e2e: 18.11 там было 92 сессии в день при CTR 0.4%, это не клиенты.

## 5. Как остановиться

- Защитная метрика хуже контроля с p < 0.05 — выключить, разобраться.
- Победитель в interleaving — короткий A/B 50/50 до первой защитной проверки (2 недели), затем
  100% и новая версия `ALGORITHM` в `recommend-score.ts`.
- Каждый эксперимент — строка в этом файле: id, даты, варианты, результат, решение.
